# Предложение первичного адаптера BingX

Пакет подготовлен по новому поручению ROOT24Oct: весь проект переводится с HTX/Huobi на криптовалютные бессрочные контракты BingX. USDT-M и COIN-M разделены; количество контрактов и совпадающих активов пока неизвестно. История HTX сохраняет свою биржу и исходные часы.

`bingx-perpetual-market.mjs.txt` — готовый текст чистого модуля: точные дескрипторы отдельных публичных запросов, разбор каталога/котировок/OI/объектных свечей/funding history и существующая форма futuresSnapshot с `data.venue=BINGX` и `data.instrument_identity`. В нём нет fetch, внутреннего перебора контрактов, SQL или разрешения native-вызовов. Производственные файлы не изменены.

В официальном статическом справочнике свечи обоих семейств — объекты, а не массивы из SKILL. В каталоге есть не-криптовалютные контракты; старый список105 не заменяет классификацию BingX. PAXG/XAUT исключаются как золото. `size:0` и торговые минимумы не считаются размером контракта. Единица OI, исходные часы mark/funding и действующий funding period остаются NULL там, где точного подтверждения нет. Разрыв между историческими funding events не считается текущим периодом выплаты.

Точный интерфейс и реальные места подключения — в identity-contract/caller-seams. Цена в единицах native-контракта может быть информационной при неизвестном multiplier, но исполнение требует независимого совпадения requested identity, price identity и идентичности исходного execution gate, а также подтверждённых единиц/ёмкости. Даже при отсутствующей идентичности новый компонент помечается BINGX, чтобы не попасть в старую ветку HTX.

`connected.mjs` содержит ОДИН новый CONTROLLED group/18 named variants, PREPARED_UNEXECUTED. Он импортирует фактическое тело предложенного модуля после проверки всех файлов и четырёх полных baseline inputs; старый реальный market-contracts используется только для нового контрпримера переноса площадки. Кейс не исполняет весь Worker, THIRD consumer, приватную сборку618 или native API. Каждый фактически возвращённый результат сохраняется до assert/следующего consumer; throw несёт partial_result, fetch восстанавливается в finally. Автор кейс не запускал.

ROOT должен отдельно связать свой новый producer и три реальные price/receipt calls, проверить полный центральный import closure и точный THIRD consumer, пересчитать общий бюджет/сутки/хранение/частоту по фактическому каталогу и получить admitted оригиналы. В проверенных конечных официальных REST/WS документах нет подтверждённого bulk/WS OI; OI на каждый контракт требует явной ротации и сохраняет настоящий возраст данных. Частота полного отчёта и лимиты этим предложением не изменены.

Официальные источники: [native API](https://bingx-api.github.io/docs/), [точный статический файл](https://bingx-api.github.io/docs/static/js/app.4dcba784df17c52faa47.js), [официальный AI reference](https://github.com/BingX-API/api-ai-skills/tree/7b1c40d29c248b18fcf418767c8e49760d1f6ef0/skills), [общий rate ceiling](https://bingx.com/en/support/articles/31103871611289). Хеши исходных документов и различия схем сохранены в official-schema-evidence. Их примеры не выдаются за реальные ответы API.

Новых providerHTTP/WS, Node/import/syntax/tests, SQL/CF/dispatch/MAIN/Telegram нет. Подключение BingX, фактический полезный охват, стоимость и native пригодность не заявлены. Локальный неизменяемый Git-пакет предназначен для обычного запрошенного чтения ROOT.
