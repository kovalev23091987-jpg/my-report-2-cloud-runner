# Реальный вход свечей для блока аномалий

Основной путь — выбранная владельцем двухступенчатая схема: уже оплаченный общий снимок105 даёт дешёвый HINT_ONLY, точные свечи/фон/внутреннюю структуру получает только ограниченное число допущенных редких кандидатов, а последующее sampled-наблюдение переиспользует существующие снимки. Полный сбор OHLCV всех105 не требуется. Пакет фиксирует реальные поля, недостающие данные редкого кандидата, обычную/пиковую модель расходов и условия отсрочки. Основной отчёт и его резервы сохраняются.

Рабочая база — `b6e85836267ed3cf9a04e64c449a4ffafd6c8d2c`; собственная ограниченная аренда `4ac5a8191f8f45d78fddb55de75ca01c39c23ed1`, owner `CODEX:SOURCES:01a14e11:1792351558335`, expiry1792356358335, exact readback/fencefalse. Все изменения — в собственном checkpoint-префиксе. Event/watch/outcome/retention/outbox остаются у третьего исполнителя; native admission, интеграция и любые подключения — у координатора.

## Основной редкий путь и бюджет

На первом шаге существующие anomaly flags, price, OI и rolling24h дают только подсказку. Разность `T24(t)−T24(t−d)` содержит одновременно вошедший новый и ушедший старый оборот; это не объём интервалаd. Новых providerHTTP для уже полученного общего снимка0. Если он передаётся в памяти, дополнительный SQL0; стоимость отдельного читателя покаNULL.

Далее выбирается конкретный допущенный редкий кандидат, независимо от основного shortlist24/deep2, без сокращения ресурсов main. Отдельный источник должен дать точный native event timeframe,20prior+1event, минутную внутреннюю структуру и не более одной bounded trade page. Получать все6 масштабов для каждого hint не предполагается. По принятому459 переиспользован условный CoinEx REST-контракт; MEXC/BingX остаются отдельными кандидатами с прежними identity/units/access blockers.

| Сценарий одного нового независимого источника | Обычный пример | Пиковый пример |
|---|---:|---:|
| Новые редкие deep admissions D/сутки |2 |10 |
| Повторный deep по умолчанию |0 |0 |
| Только узкие данные:3HTTP на deep |6/сутки,186/31день |30/сутки,930/31день |
| Условный cold вариант: до5HTTP на каждое новое событие |до10/сутки |до50/сутки |
| Дополнительный глубокий пересмотр R при новом недостающем факте и отдельном допуске |4 |20 |
| Принятый459 расчёт3×(D+R), переиспользован без rerun |18/сутки |90/сутки |

Это сценарии, не измеренная редкость, расписание или новые caps. Полный счёт остаётся `M+I+3×(D+R)`; фактические metadataM/identityI и nativeSQL/R/W неизвестны. Cold5 предполагает, что одна документированная identity lookup действительно пригодна для точного актива. При общем свежем metadata второй актив условно добавляет4HTTP: два cold кандидата требуют9, а не5. Такая арифметика не разрешает acquisition.

После всего main/manual и резерва nextfull нужен **фактический** остаток каждой отдельной общей/source/provider/IP/day/month квоты и native бюджета. При остаткеHTTP5 может поместиться только один условный cold пакет; при unknown native cost/непригодной identity/отказе source admission не запускается ни один. Остальные hints получают DEFERRED/PENDING_DATA с исходными часами и причиной. Отсрочка не является no-event или ошибкой рынка; нет автоматического provider/spot escalation, retry, quota alias, сброса unknown или возврата резерва. Поздний разбор не наследует ранний firstknown/early flag.

Watch по умолчанию использует уже полученные5m snapshots с0 новых providerHTTP, а не новый глубокий сбор каждые5минут. Это отдельная HTX reference-price траектория с сохранённым venue/quote/basis, а не восстановленная внутрисвечная история CoinEx. Новый native reader и допустимость outcome требуют своих границ/ACK/anchor; при нехватке данных результат censored.

Выбор редких q активов по массовому фильтру уменьшит запросы, но оставит непроверенную часть105; это нужно отражать в denominator, а не объявлять полное обнаружение.

Подписки4 масштабов дают420 topics,6 масштабов630; пригодность одного соединения для них не доказана. Веб-сокет разделяет HTTP upgrade, control messages, data frames и закрытые свечи. При условном500мс обновлении всех630 topics получаются108864000 frames/сутки, при250мс217728000. Это сценарии нагрузки, не измерения и не гарантия частоты HTX. Записывать каждый update как отдельную свечу нельзя.

128 активных watch slots — события, а не128 уникальных активов. Несколько событий/ревизий могут использовать один exact source key. Нужна дедупликация по venue/market/native instrument/epoch/timeframe;128×6 самостоятельных acquisition не предполагаются.

При хранении одной свечи в одной строке логические свечные количества дают нижнюю оценку base-row insert, но не native rows_written: упаковка, индексы, admission/journals, ACK, retention и уже работающий main меняют стоимость. Прежние unknown/reservations, main/manual приоритет и резерв следующего full59000R920W сохранены.

Native дневной/недельный UTC-offset нельзя угадывать как полночь/понедельник: требуется проверить фактические ID и отдельно подтвердить сетку. Reconnect требует bounded backoff, последних закрытых ключей, явных gaps и отдельного backfill admission. Постоянный процесс/host, его uptime и стоимость ещё не квалифицированы; часовой автоподхват чата не служит постоянно открытым data feed.
