# МОЙ ОТЧЁТ 2 ЕДИНОЕ ТЕХНИЧЕСКОЕ ЗАДАНИЕ НА ДОРАБОТКУ СИГНАЛОВ РАННЕГО ПОИСКА ДАННЫХ И ОТЧЁТОВ

Дата: 2026-09-24  
Тип: единое консолидированное DELTA-ТЗ к существующей системе  
Статус: требования для проверки и завершения candidate-реализации  

## 1. Назначение документа

Этот документ объединяет все последние требования к рабочим сигналам на вход, раннему поиску монет до разгона, анализу свечей и микроструктуры, использованию нескольких бирж, ликвидациям, Telegram и ручному отчёту.

Исполнитель не должен считать, что каждый пункт отсутствует. Сначала он обязан проверить текущий код, последний candidate-checkpoint, тесты и фактические runtime-связи. Уже работающие части сохраняются. Частично работающие части расширяются минимальной DELTA. Новая параллельная архитектура запрещена.

Задача считается выполненной не по наличию файлов или unit-тестов, а только при доказанной цепочке:

`данные → нормализованный факт → аналитический признак → отбор или состояние → канонический результат → нужная форма отчёта`.

## 2. Обязательная исходная точка

Перед любыми изменениями:

1. Загрузить актуальные облачные документы:
   - `MY_REPORT_2_MASTER_STATE.md`;
   - `MY_REPORT_2_LATEST_CHECKPOINT.json`;
   - `MY_REPORT_2_CHANGELOG.md`;
   - `MY_REPORT_2_ENTRY_SIGNAL_EARLY_CANDIDATE_PROGRESS_CHECKPOINT_20260924.md`;
   - это единое ТЗ.
2. Проверить фактический GitHub `main`, текущую candidate-ветку, её HEAD, рабочее дерево и результаты последних тестов.
3. Не возвращаться к более старому состоянию, если после указанного checkpoint существует более новый проверенный candidate-checkpoint.
4. Старый HTML, старые Master-файлы и документы со статусом `SUPERSEDED` не использовать как текущую исходную точку.

Последняя подтверждённая production-база на момент составления документа:

`08d98579c5ecbeb4de426ffeb1160f25ece52708`

Последний сохранённый статус candidate-работы:

- `IN_PROGRESS_CANDIDATE_ONLY`;
- focused suite `52/52 PASS`;
- production не изменён;
- D1-схема не изменена;
- получатели Telegram не изменены;
- автоматическое исполнение не включено.

Если фактическое состояние новее, использовать новое состояние только после проверки его происхождения, тестов и checkpoint.

## 3. Главное правило не переделывать выполненное

Исполнитель обязан сначала создать матрицу по каждому пункту этого ТЗ:

| Статус | Значение |
|---|---|
| `IMPLEMENTED_AND_WIRED` | Код существует, вызывается runtime, влияет на предусмотренный результат и подтверждён сквозным тестом |
| `IMPLEMENTED_PARTIAL` | Часть цепочки работает, но отсутствует источник, consumer, вывод или доказательство |
| `SHADOW_OR_DATA_ONLY` | Данные собираются, но не влияют на поиск, решение или пользовательский отчёт |
| `MISSING` | Реализации нет |
| `BLOCKED` | Нужны отдельное разрешение, миграция, секрет, источник или решение владельца |

После матрицы внедрять только `IMPLEMENTED_PARTIAL` и `MISSING`. Для `SHADOW_OR_DATA_ONLY` подключить минимальный существующий bridge, если этот блок по ТЗ обязан влиять на поиск или вывод. `IMPLEMENTED_AND_WIRED` не переписывать.

### 3.1. Обязательная сверка исходного ТЗ исполнителя с новыми дополнениями

До изменения кода исполнитель обязан взять:

1. полное исходное ТЗ, которое уже находится в его рабочем чате и по которому он начал реализацию;
2. все его текущие изменения, тесты и checkpoint;
3. настоящее единое ТЗ со всеми добавленными после старта требованиями.

Затем выполнить построчную и посмысловую сверку. Нельзя проверять только новые дополнения и нельзя заменить исходное ТЗ этим документом без сравнения. Итогом должна стать одна Requirement Coverage Matrix, содержащая каждый пункт из обоих источников.

Обязательные столбцы матрицы:

| Поле | Что указать |
|---|---|
| `requirement_id` | Устойчивый номер требования |
| `source` | `ORIGINAL_TZ`, `NEW_ADDITION` или `BOTH` |
| `original_wording` | Краткий точный смысл требования из исходного ТЗ |
| `unified_wording` | Итоговая формулировка с учётом новых уточнений |
| `implementation_status` | Один из пяти статусов этого раздела |
| `code_location` | Файл, функция и runtime-вызов |
| `test_evidence` | Название теста и результат |
| `runtime_effect` | Как требование влияет на discovery, rank, state или output |
| `remaining_work` | Что конкретно ещё требуется |
| `conflict_resolution` | Как разрешено расхождение старого и нового требования |

Правила сверки:

- ни один пункт исходного ТЗ не удалять молча;
- ни одно наше новое дополнение не считать необязательным из-за отсутствия в исходном ТЗ;
- совпадающие пункты объединять со статусом `BOTH`, не реализовывать дважды;
- если новое уточнение меняет старое требование, применять новую формулировку только в пределах явного уточнения, сохраняя остальную старую логику;
- любое реальное противоречие вынести отдельной строкой и разрешить по приоритету актуального MASTER/checkpoint и более нового явного требования пользователя;
- если определить приоритет невозможно, остановить только конфликтующий пункт и задать один конкретный вопрос, продолжая независимые работы;
- наличие кода без runtime-вызова, consumer и сквозного теста считать максимум `IMPLEMENTED_PARTIAL`;
- отсутствие пункта в созданной матрице считается провалом приёмки.

Перед началом реализации исполнитель обязан сообщить итоговые количества:

- требований только из исходного ТЗ;
- новых требований;
- объединённых требований `BOTH`;
- уже полностью реализованных;
- частично реализованных;
- отсутствующих;
- заблокированных;
- найденных противоречий.

После реализации эта же матрица обновляется фактическими доказательствами. Закрывать задачу до повторной сверки запрещено.

## 4. Целевой результат

Система должна:

- круглосуточно искать интересные Long и Short идеи среди реально торгуемых HTX Futures;
- находить как готовые точки входа, так и ранние кандидаты до основного движения;
- не превращать каждый результат в вечное наблюдение;
- выдавать `ENTRY_NOW_ANALYTICAL`, если фактические условия входа выполнены;
- выдавать `WAIT_FOR_TRIGGER` только с точным условием перехода во вход;
- не выдумывать сигнал, если условий нет;
- анализировать данные с наиболее полного и свежего подключённого источника, а не начинать анализ обязательно с HTX;
- использовать HTX как обязательную биржу существования фьючерса и фактического исполнения;
- формировать один канонический аналитический результат;
- выводить его в двух разных закреплённых формах: полной ручной и компактной Telegram.

## 5. Что запрещено менять в рамках этой DELTA

Без отдельного письменного разрешения пользователя запрещено:

- менять `main` и production;
- выполнять production promotion;
- использовать force push;
- менять веса `35/30/20/15`;
- автоматически ослаблять Hard Gates или пороги;
- менять торговые стратегии;
- включать автоматическое исполнение сделок;
- обозначать некалиброванный балл статистической вероятностью;
- включать `ENTRY_NOW_VALIDATED` без статистической валидации;
- менять получателей Telegram или секреты;
- повторять Telegram-canary;
- включать отдельную V3 network-рассылку;
- выполнять D1-миграцию;
- выполнять Cloudflare deploy.

Если D1-миграция технически необходима, подготовить миграцию, тесты, rollback и точное обоснование, но остановиться до применения и запросить отдельное разрешение.

## 6. Одна аналитика и две закреплённые формы

Обязательная архитектура:

`один snapshot → одно аналитическое ядро → один canonical result → два существующих formatter`.

### 6.1. Общая часть

Telegram и команда `Создай мой отчёт 2` обязаны использовать одинаковые:

- universe и правила допуска;
- snapshot данных;
- Capability Registry;
- source-exhaustion receipts;
- нормализацию метрик;
- scoring;
- Hard Gates;
- state router;
- причины, доказательства и Data Quality;
- entry, trigger, invalidation, targets и liquidation zones.

При одинаковом `snapshot_id` и `run_id` кандидаты, направление, баллы, состояние и фактические причины должны совпадать.

При разном времени запуска результаты могут отличаться только из-за нового состояния рынка. В каждом выводе указывать время снимка. Разница кандидатов без разницы snapshot должна считаться ошибкой.

### 6.2. Разные формы

- Telegram сохраняет свою закреплённую сегодня компактную форму.
- Команда `Создай мой отчёт 2` сохраняет свою отдельную закреплённую полную форму.
- Нельзя заменить Telegram ручным шаблоном.
- Нельзя сократить ручной отчёт до Telegram-шаблона.
- Исправляется общее аналитическое содержание, а не смешиваются два formatter.

## 7. Команда ручного запуска

Команды `Создай мой отчёт 2` и `Создай мой отчет 2` должны без дополнительных вопросов запускать полный новый анализ текущего рынка.

Команда обязана:

- загружать актуальные правила и checkpoint;
- получать новый рыночный snapshot, а не пересказывать старый отчёт;
- запускать тот же canonical pipeline, что используется автоматическим Telegram runtime;
- применять все подключённые доступные источники;
- использовать полную закреплённую форму ручного отчёта;
- показывать время snapshot и причины изменения списка относительно предыдущего запуска.

Если connector недоступен только в конкретном запуске чата, указывать `ИСТОЧНИК НЕДОСТУПЕН В ЭТОМ ЗАПУСКЕ`, а не утверждать, что рыночных данных не существует.

## 8. Universe и обязательные фильтры

### 8.1. Биржа исполнения

Торговым кандидатом может быть только монета с доказанным активным и торгуемым HTX Futures-контрактом.

До Deep Check подтвердить:

- точный symbol и contract identity;
- base и quote;
- contract type;
- multiplier и units;
- status `tradable`;
- mark и index consistency;
- отсутствие ошибочного alias mapping.

Отсутствие HTX Spot не исключает монету, если HTX Futures существует и внешний Spot подтверждён.

### 8.2. Минимальная ликвидность

Обязательный inclusive gate:

`HTX Futures rolling 24h monetary turnover >= 100 000 USD-equivalent`.

Требования:

- использовать денежный оборот, а не количество контрактов без пересчёта;
- учитывать multiplier и quote currency;
- timestamp и freshness обязательны;
- missing/stale/rate-limit не считать нулём;
- неподтверждённый оборот блокирует ENTRY до получения факта;
- тесты на `99 999`, `100 000`, `100 001` обязательны.

### 8.3. Существующие защитные фильтры

Сохранить действующие исключения явно мёртвых инструментов, ложных контрактов и аномально разрушенных активов, включая действующее правило для месячного падения порядка 97 процентов. Не ослаблять их ради увеличения числа сигналов.

## 9. Data first cross venue router

HTX не является обязательной первой точкой аналитического поиска. По каждой метрике primary source выбирается динамически по полноте, свежести, authority, coverage и health.

Использовать только реально подключённые и проверенные raw, JSON или structured endpoints:

- HTX;
- Binance;
- Bybit;
- OKX;
- Gate;
- Hyperliquid только для тех метрик, где существует фактический connector и receipt;
- другие уже подключённые источники проекта.

Наличие названия источника в allowlist не считать рабочим подключением.

### 9.1. Capability Registry

Для каждой метрики хранить:

- provider и venue;
- symbol или contract mapping;
- market type;
- units и multiplier;
- интервалы;
- history depth;
- freshness SLA;
- coverage;
- health и rate-limit state;
- authority rank;
- timestamp последнего успешного ответа.

### 9.2. Source exhaustion

До `DATA_MISSING` необходимо:

1. определить все подходящие реально подключённые источники;
2. проверить identity и сопоставимость;
3. запросить лучший источник;
4. при missing, stale, rate limit, timeout или unsupported перейти к следующему;
5. при конфликте вызвать третий независимый источник, если он доступен;
6. сохранить Source Exhaustion Receipt.

Receipt содержит metric, snapshot/candidate IDs, фактический порядок попыток, source, timestamp запроса и данных, outcome, units, interval, выбранное значение или доказательство исчерпания и влияние на Data Quality/eligibility.

Обязательная семантика:

- `missing != zero`;
- `stale != current`;
- `rate limit != no signal`;
- `unsupported != zero`;
- `timeout != zero`;
- `conflict != average`.

### 9.3. Cross venue conflict

Перед сравнением проверить underlying, contract, market type, timestamp, funding interval, units, multiplier и freshness.

Реальное расхождение сохранять как `CROSS_VENUE_DIVERGENCE`. Значения не усреднять. Неразрешённый критичный конфликт блокирует ENTRY. Некритичный конфликт снижает Data Quality и показывается в отчёте.

### 9.4. Роль источников

- Spot price, volume, flow и depth: выбирать наиболее полный источник, обычно среди Binance, OKX и других доступных.
- Futures OI, funding и trajectory: сопоставлять HTX, Binance, Bybit, OKX и Gate там, где connector реально активен.
- HTX: обязательный execution gate, BBO, spread, depth, slippage, mark/index и фактические параметры сделки.
- Liquidations: фактические cross-venue события отдельно от расчётных зон.
- Smart Money и positioning: только источники с доказанным connector, identity и coverage.

## 10. Постоянный сбор данных и бюджет

Проверить фактическое состояние существующих collectors. Не считать сбор круглосуточным только по наличию файла или таблицы.

Для каждого collector доказать:

- он запускается production/candidate runtime;
- получает реальные данные;
- сохраняет freshness и coverage;
- переживает reconnect;
- не создаёт дубли;
- его данные читаются аналитическим consumer;
- состояние отражается в health telemetry.

Если coverage частичное, сохранить честный статус `PARTIAL_REALTIME_COVERAGE`.

Горячий цикл должен оставаться ограниченным по запросам и D1. Тяжёлую историю 30–90 дней вынести в существующий maintenance/backcheck lane либо другой уже предусмотренный фоновый путь. Не сохранять каждый trade в D1; сохранять агрегаты, события, признаки, изменения состояний и outcomes.

## 11. Поиск кандидатов до разгона

Не создавать второй early-search engine. Переиспользовать существующие:

- Stage-0 scan;
- V3 early sidecar;
- `v3_early_candidate_wave`;
- Fast Move Watch;
- Opportunity Intelligence;
- Multi-Wave;
- существующий Deep Check scheduler;
- текущие persistence и budget guards.

### 11.1. Обязательный bridge

Ранний признак должен не только сохраняться в shadow:

1. Stage-0/V3 early trigger создаёт typed receipt.
2. Receipt повышает приоритет той же монеты в существующей очереди Deep Check.
3. Deep Check выполняет полный анализ.
4. Результат влияет на rank/state в рамках существующих правил.
5. EARLY CANDIDATE появляется в canonical result.
6. Он отображается в полной ручной форме и, когда достоин отдельного сообщения, в компактной Telegram-форме.

Ранний признак не может обходить Hard Gates, создавать автоматический вход или самовольно менять score weights.

### 11.2. Раздел ручного отчёта

Полный отчёт всегда содержит раздел:

`РАННИЕ КАНДИДАТЫ ДО ДВИЖЕНИЯ`

Если кандидатов нет, раздел всё равно присутствует и кратко сообщает:

- сколько инструментов проверено;
- сколько отсеяно по обороту и HTX identity;
- сколько имело аномалию;
- почему ни один не прошёл дальше.

## 12. Анализ свечей и скрытого объёма

### 12.1. Поиск событий

Для всех допустимых инструментов искать аномальные события на:

- 15 минут;
- 1 час;
- 4 часа;
- 1 день.

История событий: минимум 30 дней; предпочтительно 60–90 дней, если это укладывается в отдельный bounded backcheck lane.

### 12.2. Разложение события

Каждое существенное событие раскладывать на полные закрытые:

- 1-минутные свечи;
- 3-минутные свечи;
- 5-минутные свечи.

Запрещены интерполяция и выдумывание пропущенных минут. Неполная минутная история блокирует окончательную классификацию и снижает Data Quality.

### 12.3. Проверяемые гипотезы

Большая красная свеча с огромным объёмом не считается автоматически накоплением. Система обязана сравнить минимум четыре объяснения:

- скрытое накопление и поглощение продаж;
- распределение;
- двусторонний перенос крупного объёма;
- ликвидационный или фьючерсный шум.

Использовать:

- effort versus result;
- body, wick, close и reclaim;
- последовательность сделок и агрессоров, если доступна;
- Spot и Futures flow;
- OI и его trajectory;
- funding и funding history;
- basis и mark/index;
- order book и depth;
- realized и projected liquidations;
- relative strength к BTC и ETH;
- последующее поведение цены после события.

Вывод обязан содержать факты, альтернативы, Data Quality и причину выбранной классификации.

### 12.4. Ранний кандидат и памп

- Монета с rolling 24h движением менее +20 процентов может попасть в ранние кандидаты.
- Монета с rolling 24h движением от +20 процентов относится к памповому сценарию и обрабатывается отдельным блоком риска и ликвидаций.
- Граница +20 процентов должна иметь точный тест.

## 13. Микроструктура и сквозное влияние

Проверить не только наличие таблиц и parsers, а фактический путь:

`collector/writer → свежая запись → feature builder → candidate rank/state → evidence receipt → report reason`.

Проверяемые данные:

- taker buy/sell flow;
- CVD или допустимый эквивалент;
- объём и число сделок;
- order book imbalance;
- spread и depth;
- basis;
- positioning trajectory;
- absorption/exhaustion;
- price response на агрессивный поток.

Если блок только data-only или advisory, это явно фиксируется. Нельзя обозначать его активным поисковым фактором без runtime consumer и сквозного теста.

## 14. Scoring и состояния

### 14.1. Канонические состояния

Один state router:

- `ENTRY_NOW_ANALYTICAL`;
- `ENTRY_NOW_VALIDATED`;
- `WAIT_FOR_TRIGGER`;
- `OBSERVE`;
- `REJECTED`.

`ENTRY_NOW_VALIDATED` остаётся выключенным до отдельной статистической калибровки и разрешения.

### 14.2. Две оценки

Сохранить две отдельные оценки по шкале 0–100:

- качество идеи;
- готовность точки входа.

В пользовательском тексте использовать только понятные русские подписи. Не использовать двусмысленную строку `Кандидат: X | Вход: Y` без пояснения. Допустимый вариант:

`Качество идеи 86/100 · Готовность входа 79/100`.

Эти оценки не называются вероятностью до завершения статистической калибровки.

Фразы `Автоматическая торговля выключена` и `Это оценка системы, а не вероятность` в Telegram и пользовательском отчёте не выводить. Эти ограничения сохраняются внутри системы и документации.

## 15. Достижимый вход и точное ожидание

### 15.1. ENTRY NOW ANALYTICAL

Сделать технически достижимым аналитический сигнал для ручного решения, когда:

- направление закрыто;
- обязательные Hard Gates пройдены;
- текущая цена находится в рассчитанной entry area;
- HTX execution facts свежие;
- spread, depth и slippage допустимы;
- fees и funding учтены;
- есть invalidation и targets;
- критичные данные закрыты или имеют допустимый status по утверждённому правилу.

Нельзя решать задачу простой заменой текста `ЖДЁМ` на `ВХОД`.

### 15.2. Entry area

Переиспользовать существующий scenario plan и устранить deadlock:

1. versioned strategy-level entry-area rule;
2. детерминированное применение к snapshot кандидата;
3. immutable receipt с rule version, inputs, диапазоном, timestamp и invalidation.

До статистической валидации разрешается только `ENTRY_NOW_ANALYTICAL`.

### 15.3. WAIT FOR TRIGGER

WAIT разрешён только с машиночитаемым Trigger Contract:

- тип trigger;
- точная цена или диапазон;
- crossing, reclaim или close semantics;
- timeframe;
- подтверждающие метрики;
- срок действия;
- условия отмены;
- evidence snapshot IDs;
- время следующей проверки.

При выполнении trigger система заново проверяет Hard Gates и переводит идею в ENTRY либо отменяет её. Бессрочный WAIT запрещён.

## 16. Комиссии funding и исполнимость

Переиспользовать существующие HTX execution adapters.

Нужны:

- versioned HTX fee schedule receipt;
- BBO;
- spread;
- depth;
- ожидаемый slippage для планируемого размера;
- holding window;
- funding interval и history;
- ожидаемые settlement events;
- итоговая оценка costs-adjusted reward/risk.

Если личный fee tier неизвестен, допускается только заранее утверждённый консервативный тариф с versioned receipt. Нулевые комиссии запрещены.

## 17. Smart Money и Supporting Risk

Аудировать и переиспользовать существующие Smart Money, Hyperliquid recorder, ByKaranteli и risk modules. Не создавать дубликаты.

Для каждой метрики определить `critical` или `optional`:

- отсутствие critical после полного source exhaustion блокирует ENTRY;
- отсутствие optional снижает Data Quality или ограничивает score, но не превращает весь блок автоматически в ноль;
- любой доступный факт сохраняется с source, timestamp, identity и coverage;
- источник считается активным только при реальном runtime-вызове и receipt.

Если эти блоки нельзя фактически закрыть, исполнитель обязан выдать точный blocker, а не общую фразу.

## 18. Памповые монеты и ликвидации

Памповая монета определяется как rolling 24h рост от +20 процентов включительно.

Для каждой такой монеты показывать:

- ближайшие значимые зоны ликвидаций сверху;
- ближайшие значимые зоны снизу;
- самые крупные дальние зоны сверху;
- самые крупные дальние зоны снизу;
- цену каждой зоны;
- расстояние от текущей цены в процентах;
- размер или относительную силу кластера;
- источник, coverage и freshness;
- отдельно realized/factual и projected/modelled зоны.

Ограничения по расстоянию нет. Показывать значимые зоны, даже если они находятся на 20, 40, 60 процентов и дальше.

Не придумывать уровни. Если после source exhaustion данных нет, это явно указывается.

## 19. Формат Telegram

Сохранить последнюю закреплённую компактную форму Telegram. Менять только наполнение, если оно ещё не соответствует требованиям.

Обязательные правила:

- только русский язык, кроме тикера, названия биржи и технически неизбежных обозначений;
- максимально короткий текст без потери ключевых фактов;
- никаких одинаковых шаблонных объяснений для разных монет;
- причины строятся из evidence receipts конкретной монеты;
- использовать точные значения, интервалы и источники;
- никаких картинок, графиков, cards, widgets, media или attachments;
- не выводить служебные фразы об автоматической торговле и вероятности;
- не спамить одинаковым состоянием без существенного изменения.

### 19.1. Если вход есть

Компактно показать:

- монету и направление;
- `Качество идеи X/100` и `Готовность входа Y/100`;
- 2–4 важнейших индивидуальных факта;
- entry area и текущую цену;
- invalidation;
- цели;
- критичные costs/funding;
- срок действия;
- liquidation zones, когда применимо.

### 19.2. Если входа нет

Сообщение обязано объяснить:

- почему монета уже интересна;
- что уже совпало;
- что ещё не совпало;
- точный trigger входа;
- срок действия;
- условие отмены;
- когда будет следующая автоматическая проверка.

Фразы вроде `монета сильнее рынка`, `OI растёт`, `активность высокая` без значений и контекста запрещены.

### 19.3. OBSERVE

OBSERVE не отправляется как повторяющийся псевдосигнал. Он допускается в сгруппированной сводке либо при новом существенном событии.

## 20. Полный ручной отчёт

Сохранить закреплённую полную форму команды `Создай мой отчёт 2`.

Она должна содержать все предусмотренные действующей формой разделы и дополнительно гарантировать наличие:

- времени snapshot и режима рынка;
- итоговых Long и Short кандидатов;
- двух оценок каждого кандидата;
- статуса ENTRY, WAIT, OBSERVE или REJECTED;
- конкретных доказательств по каждой монете;
- точной entry/trigger/invalidation/targets логики;
- источников, Data Quality и конфликтов;
- раздела `РАННИЕ КАНДИДАТЫ ДО ДВИЖЕНИЯ`;
- отдельного раздела памповых монет и двухсторонних ликвидаций;
- понятного итога, если подходящих входов нет.

Ручной отчёт подробнее Telegram, но использует те же факты и состояние.

## 21. Outcome journal и статистическая проверка

Read-only выгрузить всех доступных кандидатов после последнего production checkpoint, включая прошедших, ожидающих и отклонённых.

Для каждого сохранить:

- snapshot и время решения;
- score и четыре блока;
- state и gate outcomes;
- причины ожидания или отказа;
- entry area или trigger;
- Data Quality и source receipts;
- движение через 15м, 30м, 1ч, 4ч и 24ч;
- MFE и MAE;
- достижение targets и invalidation;
- результат с учётом комиссий и funding.

Ответить числами:

- существует ли технический потолок score ниже 75;
- сколько хороших движений пропущено техническими блокировками;
- какие фильтры полезны, а какие блокируют почти всегда;
- precision/recall по режимам и направлениям;
- сколько реальных сигналов можно ожидать без искусственного ослабления правил.

Не менять веса и пороги автоматически. Преобразование балла 0–100 в статистическую вероятность разрешается только после достаточной выборки, out-of-sample проверки и отдельного утверждения.

## 22. Защита от бесполезных модулей

Для каждого заявленного аналитического блока предоставить Integration Coverage Proof:

1. producer существует и вызывается;
2. receipt или нормализованный факт создаётся;
3. consumer читает этот результат;
4. изменение fixture меняет предусмотренный rank/state/reason;
5. результат появляется в canonical result;
6. соответствующий formatter его отображает;
7. telemetry показывает использование;
8. при разрыве цепочки тест падает.

Если блок не должен влиять на rank, это явно документируется как informational/advisory. Нельзя скрытно считать его поисковым фактором.

## 23. Обязательные тесты

### 23.1. Состояния и вход

1. Полностью валидный fixture создаёт `ENTRY_NOW_ANALYTICAL` end-to-end.
2. Слабый fixture не создаёт ложный вход.
3. Near-miss создаёт точный WAIT trigger, expiry и cancellation.
4. Выполнение trigger вызывает повторную проверку и переход в ENTRY либо отмену.
5. Истёкший WAIT закрывается.

### 23.2. Data first и источники

6. Binance или OKX выбирается primary, если данные лучше HTX.
7. ONG: HTX Futures есть, HTX Spot нет, внешний Spot есть — кандидат не исключается.
8. Rate limit не превращается в ноль; используется fallback.
9. Timeout, stale и unsupported не превращаются в ноль.
10. HTX OI растёт, Binance OI падает — значения не усредняются.
11. `DATA_MISSING` невозможен без Source Exhaustion Receipt.
12. Нет HTX Futures или контракт неторгуемый — торговый кандидат блокируется.

### 23.3. Оборот

13. `99 999` — не проходит.
14. `100 000` — проходит границу.
15. `100 001` — проходит.
16. Stale или missing turnover не считается нулём и не создаёт ENTRY.

### 23.4. Ранний поиск и свечи

17. Ранняя аномалия реально повышает приоритет и приводит монету в Deep Check.
18. Без аномалии приоритет не повышается.
19. Неполные 1м/3м/5м данные не создают финальную классификацию.
20. Красная свеча с объёмом различается как absorption или distribution по последующим фактам, а не по цвету.
21. Backcheck не использует будущие данные.
22. Есть negative control group.
23. Монета до +20 процентов может быть ранним кандидатом; от +20 процентов переходит в pump handling.

### 23.5. Микроструктура

24. Реальный writer создаёт свежую запись.
25. Consumer превращает её в feature.
26. Feature меняет rank/state либо доказанно формирует informational reason.
27. Тест падает, если модуль существует, но его output никто не потребляет.

### 23.6. Ликвидации

28. Границы движения: 19,99; 20; 30; 50; 70 процентов.
29. Для pump есть сильные зоны сверху и снизу.
30. Дальние зоны 20, 40, 60 процентов и дальше не отбрасываются только из-за расстояния.
31. Realized и projected не смешиваются.
32. Отсутствующие данные не заменяются выдуманными уровнями.

### 23.7. Форматы

33. Две разные монеты не получают одинаковый блок причин.
34. Каждая причина связана с evidence receipt.
35. Telegram только plain text и русский пользовательский текст.
36. В Telegram нет visual/media/attachment/card/widget/chart.
37. В Telegram нет запрещённых служебных фраз.
38. WAIT объясняет, почему интересно, что уже есть и чего ждём.
39. Одинаковый snapshot даёт одинаковые факты, кандидатов и состояния в Telegram и ручном отчёте.
40. Formatter Telegram остаётся компактным, formatter ручного отчёта остаётся полным.
41. Разные кандидаты при разных snapshot объясняются временем данных.
42. Команда `Создай мой отчёт 2` запускает новый полный анализ без уточняющих вопросов.

### 23.8. Costs risk и безопасность

43. Нулевые fees без receipt запрещены.
44. Funding учитывает interval и предполагаемый holding window.
45. Critical Smart Money или Supporting Risk gap после exhaustion блокирует ENTRY согласно утверждённой классификации.
46. Repeat suppression работает только при отсутствии существенных изменений.
47. Resource budget и D1 guards проходят.
48. Failure injection проходит.
49. No-lookahead проходит.
50. Полная существующая regression suite проходит без ухудшений.

## 24. Порядок выполнения

1. Exact production и candidate readback.
2. Матрица `IMPLEMENTED_AND_WIRED / IMPLEMENTED_PARTIAL / SHADOW_OR_DATA_ONLY / MISSING / BLOCKED`.
3. Отдельная сверка `ORIGINAL_TZ` против `NEW_ADDITION` с единой Requirement Coverage Matrix.
4. Карта producer-consumer-output для каждого блока.
5. Минимальные изменения только разорванных связей.
6. Focused tests.
7. Integration и end-to-end tests.
8. Полная inherited regression suite.
9. Resource-budget и failure-injection tests.
10. Bounded historical replay без записи в production.
11. Повторная сверка каждого пункта исходного ТЗ и каждого нового дополнения.
12. Новый candidate checkpoint и changelog.
13. Сохранение результатов в облаке.
14. Остановка до любого действия, требующего отдельного разрешения.

## 25. Критерии окончательной приёмки

Работа на candidate-уровне считается завершённой, только если:

- каждый пункт ТЗ имеет статус и доказательство;
- каждый пункт исходного ТЗ исполнителя и каждое новое дополнение присутствуют в общей Requirement Coverage Matrix;
- по матрице нет потерянных или молча удалённых требований;
- нет второй параллельной архитектуры;
- валидный `ENTRY_NOW_ANALYTICAL` достижим end-to-end;
- WAIT всегда имеет точный trigger;
- ранний candle/microstructure признак реально влияет на существующий Deep Check priority;
- cross-venue работает data-first, а HTX остаётся execution gate;
- source exhaustion доказан receipts;
- turnover gate 100 000 работает;
- pump от +20 процентов показывает сильные зоны сверху и снизу без distance cap;
- один canonical result питает два разных закреплённых formatter;
- Telegram индивидуален, короток и полностью текстовый;
- ручной отчёт полный и содержит ранних кандидатов;
- исторический replay представлен числами;
- focused, end-to-end, budget, failure-injection и regression tests PASS;
- production не изменён.

## 26. Финальный отчёт исполнителя

В финале сообщить:

1. точную production-базу;
2. candidate branch и SHA;
3. матрицу статусов всех разделов этого ТЗ;
4. отдельную итоговую сверку `ORIGINAL_TZ / NEW_ADDITION / BOTH`, включая количество и список всех требований;
5. подтверждение, что ни один пункт исходного ТЗ и ни одно новое дополнение не потеряны;
6. точные изменённые файлы;
7. какие существующие компоненты переиспользованы;
8. какие разорванные связи найдены и закрыты;
9. фактически активные источники по каждой метрике;
10. доказательство раннего поиска и микроструктурного consumer;
11. доказательство достижимого ENTRY;
12. доказательство точного WAIT;
13. результаты historical replay с числами;
14. parity Telegram и ручного отчёта;
15. результаты всех обязательных тестов;
16. новый checkpoint и контрольные суммы;
17. изменился ли production — ожидается `NO`;
18. какие действия требуют нового отдельного разрешения.

Не писать `всё внедрено`, если хотя бы для одного обязательного блока отсутствует runtime-вызов, consumer, end-to-end доказательство или пользовательский вывод.
