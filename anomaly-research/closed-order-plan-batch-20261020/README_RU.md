Связанный OFFLINE-пакет: порядок закрытых свечей, повторные receipt и план исходов

Изменены три существующих исследовательских модуля. Production не импортируется и не меняется. Старые testcase, fixtures, frozen результаты и сохранённые карточки не переписаны. Порог, стратегия, score, ранжирование, лимиты и паузы проекта прежние.

В observer время свежего snapshot больше не заменяет порядок закрытых окон. Курсор сохраняет последнее принятое окно, его материальный hash и исходные часы. Более старое окно не меняет гипотезы, но свежая цена и очередь продолжают обновляться. Повтор того же окна с другой квитанцией не создаёт переход; другая геометрия того же окна возвращает конфликт без изменения состояния. Для старого watch без курсора прошлый порядок не выдумывается: окно не позднее уже сохранённого source time не применяется к гипотезам. Следующее действительно новое окно может продолжить наблюдение. Уже опровергнутый watch не открывается заново.

Для confirmation масштаба крупнее исходного теперь нужен явный confirmation_alignment_offset_ms. Фаза15m не определяет фазу1w. Значение можно передать из существующего confirmationVerdict, который требует отдельную native grid. Сам observer не проверяет подлинность внешнего grid receipt и не создаёт native qualification. Для того же или более мелкого делящегося масштаба прежний offset выводится из карточки; противоречащий явный offset отвергается. В новом контрольном входе Monday offset4дня от Unix epoch — CONTROLLED, не полученная у HTX нативная сетка.

В outcomes одинаковые instrument/source_ts/price не становятся двумя наблюдениями из-за received_ts или новой raw-ссылки. Выбирается наиболее ранний уже доступный receipt; число ценовых samples не растёт. Отдельно считаются исключённые повторы и число различных proof-ссылок сверх одной на точку, независимо от порядка входа. Разные цены одного source time по-прежнему дают INCOMPLETELY_OBSERVED. Пропуски, будущая недоступная информация, LONG/SHORT и правила first-passage прежние. Summary проверяет новые счётчики; контракт только последних frozen результатов не заменён историей PENDING→final. Старые итоги автоматически не пересчитываются.

В outbox появился optional outcome_plan. Он должен точно воспроизводиться существующим commitOutcomePlan и соответствовать всем объявленным ячейкам logical event/horizon/direction. Hash фиксируется в событии и каждом новом outbox. Пороги5% и10% могут иметь одинаковые ключи ячеек, но теперь не одинаковую привязку плана. У привязанного события нельзя сменить или убрать план; у его ACK нужен тот же plan hash. Старый непривязанный event остаётся непривязанным: поздний план не выдаёт ему ретроспективный commit. Legacy-вызовы без плана сохраняют прежний API. Все ACK и SENT этого протокола — CONTROLLED_SIMULATED_ACK, actual_send=false, native_persistence_qualified=false.

Один новый callable: runClosedOrderPlanConnected({baseline_root,candidate_root,repo_root,budget_receipt_path}) из connected.mjs. Все аргументы — локальные пути координатора. baseline_root содержит полный checkout frozen base из manifest; candidate_root — тот же дерево с тремя after-модулями. repo_root содержит этот frozen пакет. budget_receipt_path — уже сохранённый координатором файл39423678954, SHAaf537fd73ad9c63897b79e397bb5b9f97e75b3d03e730c989a73a921ef7db7b0, не новый запрос к базе. Проверка использует его unknown1 только как запрет независимого допуска после simulated ACK, не исследует rooterror и не закрывает native cost. Остальные нулевые budget inputs в этом control — заглушки, а не фактический свободный остаток.

На входе переиспользуются exact sample-inputs и witness ранее принятого BTC/HTX пакета. Для новой цепочки берутся21 сохранённая15m свеча BTC futures. Их native epoch, concrete quote unit и настоящий first-known/body ACK остаются неизвестны; actual typed admission закрыт. Контрольная карточка строится отдельно с именами CONTROLLED, BACKFILLED/CONTROLLED cohort и явно условным instrument binding. Числа исторических свечей используются для геометрии; будущая минутная/недельная цена, known-time anchor, очередь, события, grid и ACK — новые CONTROLLED inputs, не рыночная история после обнаружения. Это не production anomaly, не timely находка и не статистическая точность.

Callable подготавливает один связанный affected case: исходные bytes → отдельный controlled detector/card → порядок закрытий/повтор/conflict → JSON restart/два события одной монеты → подтверждение и опровержение → план/цензурированный исход → draft/outbox → exact-plan ACK после UNKNOWN_SEND → независимый отказ admission при сохранённом unknown. Внутри он также устанавливает новые baseline counterexamples на before-модулях. Это не запуск старых testcase или старого replay/cohort.
