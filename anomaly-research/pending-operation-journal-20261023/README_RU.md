Конкретный разрыв: run() удерживает effective prepared и reconciliation Map только до потери процесса. Текущий fs-wrapper сохраняет ограниченные метаданные уже после ответа hook. Между validated prepared → COMMIT transport → known reply → READBACK → завершением hook полный запрос и известный ответ не имеют восстанавливаемой локальной записи. Предыдущая CONTROLLED проверка сама передавала pending DTO новому процессу; она не доказывает автоматический журнал. Точные исходные фрагменты и hashes — source-evidence.json; старые проверки не повторялись.

Предложение расширяет тот же runner fs-wrapper. PRIVATE файл report2-anomaly-domain-pending.private содержит неизменный opid, logical key, expected_revision, first_known_ts и полный канонический prepared text. Перед потенциальным WRITE/READBACK IO сохраняется точный intent; известный SDK reply записывается до возврата в kernel и следующего SQL. После асинхронной записи intent вновь проверяются current parent/usage/remaining projection. Unknown usage ограждается немедленно после settle, до fs-await. Если сохранение известного ответа не закрылось, сам известный ответ остаётся в returned result, следующий SQL запрещён; неустойчивую запись нельзя выдавать за сохранённую.

Каждая замена делает bounded read/hash check, exclusive immutable .step-NNN claim, fsync, .next exclusive create, rename, fsync родителя и точный readback. Метка содержит previous/next SHA и identity. Она сохраняется после rename: задержавшийся писатель не сможет заново занять ту же последовательность после исчезновения .next. Незавершённая .next/следующая метка, отсутствующая последняя метка, конфликт SHA/identity/operation, неверный mode, symlink, JSON/hash/bound или потерянный ожидаемый файл останавливают работу. Чужие и собственные неоднозначные метки автоматически не удаляются и не продвигаются.

Существующая metadata-квитанция получает только маленький pending_checkpoint: SHA/identity hash/sequence/count, без prepared и SQL replies. Обычный workflow выгружает runtime/report2-anomaly-domain-receipts.json по точному имени; новый .private и .step-* не добавлены в uploads. Данные и private carriers не публикуются в Git. Файл создаётся mode0600. Коррупция либо несовпадение независимого expected SHA не становятся пустым состоянием.

Явная начальная запись требует INITIALIZE_EMPTY, отсутствующих file/.next/.step-001 и exclusive create. Это отдельное доверенное первоначальное действие, не значение по умолчанию для каждого нового job. Повторное открытие требует независимого точного expected SHA и identity generation/source_head/cloud_run_id/reservation_id/day_utc. Нельзя вычислить новый доверенный expected SHA из спорного файла и считать это recovery. SHA после каждой фазы доступен через checkpoint; его независимое сохранение и способ передачи между executions остаются обязанностью ROOT. Несовпадение SHA после аварии вызывает отказ, даже если файл выглядит правдоподобно.

Восстановление незавершённого/unknown события возвращает тот же exact prepared/opid/revision и известные сохранённые ответы. Не вызываются prepare callback, новый ORIGIN, WRITE или READBACK. Новые нулевые SDK counters не очищают retained_prior_usage/unknown. Сохранённый неизвестный исход останавливает новый parent SQL: preflight стоит до loadWorker/buildEnv/новой D1 reservation; повторно открытый controller ограждает и прямые SDK обращения. Это восстановление точной stop/reconciliation точки, не автоматический повтор WRITE и не автоматическое закрытие unknown. Новый readback позднее требует отдельного обычного actual admission ROOT; этот пакет его не выдаёт.

Успешно закрытая запись остаётся в bounded local history; записи не вытесняются. До16 operations/двух logical keys в пределах прежнего controller envelope. Идентичность исходных card/descriptor/plan/first_known сохраняется как часть exact prepared. После16 записей или байтового предела новая операция отказывается до транспорта. Native policy остаётся NULL/defaultOFF; без закрытого journal handle capability не устанавливается. Новый env EXPECTED_SHA не добавлен в workflow и ничего не активирует.

Предел: это local same-workspace continuity. fsync/readback не доказывают power-loss durability, CAS распределённого backend, сохранение ephemeral GitHub disk, native commit/ACK, installed schema, native расходы, независимое105-наблюдение или Telegram. Предложение не переносит старую reservation/потраченные unknown в новую родительскую аренду. При смене source head/cloud run/day/reservation нужен отказ и отдельное решение ROOT, а не новый opid/пустой journal. Все эти launch prerequisites остаются открытыми.
