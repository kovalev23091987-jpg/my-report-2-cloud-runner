# Будущая связь запроса и серверного расхода

Конечное поручение координатора от 22 октября: подготовить только серверную половину будущих cost receipts. Старый UTC22 unknown1 не имеет общего request ID и этим пакетом не восстанавливается. Его стоимость, резервы и запреты сохраняются. Автор не выполняет Node, imports, syntax checks, tests, SQLite/SQL, семантику приложения, git apply, provider/native/CF/MAIN/deploy/Telegram.

Единственный общий файл для предложения THIRD — `runner/sql-bridge-counter-repair.mjs`: новый named export добавляется в конец. Существующие counter repair, version metadata и все прежние байты сохраняются. Новая функция принимает только точный strict06603 Worker, который координатор получает существующей production repair-функцией из сохранённого actual70c fixture. Старые тестовые exports не импортируются и не вызываются.

Фиксированный заголовок — `x-report2-request-id`. Допустим только lowercase canonical UUIDv4 из 36 символов: `^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`. SOURCE создаёт его один раз после beforeRequest admission, только при nativeQueryReceipts===true. Клиентское поле — `client_request_id`, серверное — `request_id`. Для batch транспортный ID один, порядок statements сохраняется. ID диагностический: не grant, dedupe, retry или reconciliation. Legacy OFF, тело, SQL, params, JSON ответа, native usage, auth, clocks, gates и лимиты не меняются.

Сервер использует уже разобранные body/op/usage и результат единственного существующего исполнения. Один ограниченный лог содержит только request_id, безопасный enum операции, точные SHA256 UTF8 полученных SQL до серверного trim, порядок, независимые известные строгие R/W либо NULL, серверный интервал, статус подготовленного ответа, DATA_DB и явные пределы/omission/qualificationfalse. Полные SQL, параметры, строки результатов, тело, секреты и raw error в лог не попадают. Нет второго SQL, fetch, clone ответа или копирования большого тела/результата. Raw/exec и неизвестные расходы сохраняют unknown. Ошибка log/hash/console не меняет исходный ответ, расходы или повторные попытки.

Пределы: существующий batch<=100; один лог<=32768 UTF8 байт. При переполнении допускается только ограниченная отметка полного omission без частичных costs/hashes, а не усечённое доказательство. Отсутствующий или неверный header не ломает legacy запрос и может не создавать лог. Результат не подтверждает доступность Cloudflare logs: для неё нужны фактические settings и будущий допущенный native event, которыми занимается только координатор.

Один новый callable `runBridgeServerCostCorrelationConnected({runtime_root,baseline_runtime_root,repo_root})` получает два фактически собранных ROOT дерева, не `src`. SOURCE меняет только SDK и native journal: в обоих деревьях618 файлов, остальные616 равны. THIRD helper — repo-only. Новый case использует фактический SDK → точные old/new06603 Worker → контролируемые D1/LocalSQLite, потерю ответа после server log, strict NULL/partial batch/thrown/raw/exec, canary, legacy, logger throw и отсутствие дополнительного I/O. Только координатор выполняет единую новую FIRST проверку и сохраняет каждый component JSON до assert/следующего компонента. Принятые21/61133 и прочие проверки не повторяются.

До FIRST: один взаимный static peer по новым immutable code/case, затем только ACK точечного исправления. Завершение: frozen отдельный PR, полное GitHub bytes/SHA/Gitblob чтение, освобождение только собственного CAS lease. Общие статусы/main/runtime/schema/наблюдаемость/квоты/паузы/стратегию/формы THIRD не меняет.
