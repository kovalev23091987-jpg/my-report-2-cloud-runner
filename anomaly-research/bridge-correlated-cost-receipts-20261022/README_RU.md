# Серверный receipt будущего расхода

После потери ответа нынешний клиент знает свой SQL и sequence, но установленный SQL bridge не имеет того же диагностического request ID. Предложение добавляет ограниченный серверный лог, который будущий допущенный запрос можно связать с клиентским журналом. Это не автоматическое закрытие расхода: даже при сохранённом server log клиентская потеря ответа остаётся unknown. Старый UTC22 unknown1 без ID этим пакетом не восстанавливается.

Новый `addExactSQLBridgeCostCorrelation(source)` добавляется в конец существующего `runner/sql-bridge-counter-repair.mjs`. Он принимает только exact strict06603 и возвращает `{source,proof}`. Прежние3935 байт helper, counter repair и version metadata сохраняются полностью. `bridge-patch.proposed.txt` — точные добавляемые байты; `repair-with-correlation.proposed.mjs` — полный ожидаемый helper; `bridge-worker.proposed.mjs` — полный ожидаемый Worker для точной сверки. Никакой из них автором не импортирован и не исполнен.

Входной `x-report2-request-id` должен быть lowercase canonical UUIDv4. Сервер не создаёт ID. Schema — `REPORT2_BRIDGE_CORRELATED_COST_V1`, фиксированный tag — `REPORT2_STRICT06603_CORRELATION_V1`; SHA всего модуля не встраивается в себя. Независимая привязка к actual version/module остаётся задачей координатора.

Лог содержит только ID, enum операции, DATA_DB, серверный интервал после auth до готового ответа, статус подготовленного ответа, исходный порядок и SHA256 точного UTF8 SQL до серверного trim, известные строгие per-statement R/W либо NULL и признаки неполноты. Интервал не является billing timestamp. Индекс0 соответствует рангу client receipt внутри одного client_request_id по сохранённому sequence; глобальный sequence не является batch index. Повторяющиеся SQL могут иметь одинаковый хеш, но сохраняют порядок. Переполненный или неполный клиентский журнал не доказывает целый batch.

Лог не содержит SQL, params, результатов, body, токена или raw error. Он создаётся после единственного существующего исполнения. Ответ сначала конструируется один раз прежним respond, затем safe logger получает существующие body/op/usage, после чего возвращается тот же Response. Нет response clone, второго SQL/fetch или большого body/result copy. Ошибка hash/encoding/console не меняет JSON, native counters, unknown, retry, auth или лимиты. Пустой/неверный header не создаёт лог и не ломает legacy запрос. Unsupported/auth отказы сохраняют прежний ранний выход.

Пределы:100 statements и32768 UTF8 байт на лог. При превышении остаётся только целая omission-отметка без частичных costs/hash. При несовпадении числа native частей с запросом известные отдельные числа сохраняются, но coverage/unknown остаются незакрытыми. Raw/exec или исключение без уже полученных счётчиков не превращаются в измеренный ноль. Каждый record явно помечен diagnostic и не разрешает reconciliation/day grant.

Один новый callable `runBridgeServerCostCorrelationConnected({runtime_root,baseline_runtime_root,repo_root})` принимает assembled ROOT, не src. До imports он связывает полный618/618 inventory,616 неизменных runtime файлов, два новых SOURCE target, полный repo-only helper и сохранённый actual70c. Во время единого центрального запуска он получает strict06603 старой production repair-функцией и новый Worker новым export; старые test modules/exports не использует.

Подготовлены12 новых групп/27 вариантов: связный old/new контрпример; потеря ответа после server log с сохранённым client unknown; одинаковые SQL в batch, частичные counters и несовпавшее число native результатов; raw/exec/thrown; реальные scalar zero inputs; legacy/header/off; auth/unsupported; logger throw; hash omission; batch100 и явно помеченная fault injection ветви UTF8-bound; разные transports/Unicode/received-before-trim hash; прежний отказ batch101. Используются настоящий SDK, точные Worker, LocalSQLite и явно контролируемые counters. Это будущая центральная проверка, не авторский PASS и не фактическая native billable cost.
