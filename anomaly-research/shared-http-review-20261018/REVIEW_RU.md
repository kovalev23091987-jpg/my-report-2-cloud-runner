## Что предложение действительно доказывает

`reconcileExplicitTransport` — pure offline arithmetic proposal. У каждого выхода, включая RECONCILED, `admission_authorized:false`; нет вызова admission, fetch, SQL, переписывания ledger или refund. Успешная сверка требует явных safe integer counter полей, уникальных известных adapter roles, суммы adapters=flow, flow+явная baseline=total=observed wrapper, total<=5 и caller grants>=transport, <=5. Вычитание N12 из **проверенной полной суммы расходов** не создаёт новый резерв.

Это проверка согласованности сообщённых счётчиков одной конкретной shared invocation. Она не доказывает действующий whole-day остаток, source/day/month/minute/credits admission, пригодность источника, независимость площадок, использованный факт, содержимое endpoint, network ACK или actual billing. Числа network_calls и observed_transport_HTTP происходят из того же producer path, а не из двух независимых native наблюдений.

Ограничение11 adapters/5 transport — верхняя граница размера/расходов, а не доказательство полноты endpoint trace. Успех arithmetic verifier не проверяет, что перечислены все запланированные zero-call adapters, что сохранены все причины отказов либо реальный endpoint order. Например, пропуск adapter с0HTTP не изменяет сумму. Не выдавать RECONCILED за «проверены все fallback» или за разрешение нового вызова. Для полного bounded trace нужна исходная expected/observed identity/count/omission привязка этой invocation; proposal правильно запрещает восстанавливать старый порядок из flattened receipts.

Это не утверждение о неправильных расходах actual APR/NEAR и не новый execution defect. **Strict result сам по себе недостаточен как единственная compact запись**, если production предложение обещает сохранить каждый known counter. На границе consumer надо оставить отдельный whitelist исходных validated network/observed/flow/baseline/grants значений и статус конфликта; malformed counter остаётся null с причиной. Можно хранить их рядом с результатом, не обязательно менять reference helper. Не выбирать min, не объявлять один witness заменой другого, не обнулять уже известный расход и не разрешать calls из-за «свободного» residual. При конфликте splits остаются null, прежние reservations/unknown не уменьшаются. Конкретные input/output без нового replay приведены в `evidence.json`.
