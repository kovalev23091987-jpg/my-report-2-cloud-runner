# Готовое предложение server-operation для anomaly-domain

Это связанное TEXT-предложение после фактического чтения существующего opportunity-store. Код и SQL автором не исполнялись. Установка, independent scheduled caller, native admission и Telegram не включены. Первый протокол — commit0205d341. Свежая база36483e132c8777c4dd9a2406c324b14af1cbf091, свой ограниченный lease — в PROTOCOL_RU.md. Privatecontract/ZIP/DDL/JS excerpts в Git не скопированы; source-references.json содержит только hashes и новый публичный BTC witness.

## Почему минимальное расширение необходимо

В фактической схеме independent opportunity-event неизменяем для любого UPDATE. Его INSERT ON CONFLICT DO NOTHING не выражает mutable watch/revisions/outbox. Existing outcome schema ограничена горизонтами до7d; funnel — счётчики, и его cleanup не защищает длительный watch. Эти таблицы, triggers, семантика и аналитический знаменатель здесь сохраняются. Нельзя спрятать новый state в funnel или снять independent_sample ради UPDATE.

Предложены две небольшие таблицы в ТОЙ ЖЕ DATA_DB: report2_anomaly_bundle_v1 и compact operation receipts. Одна INSERT-view с INSTEAD OF trigger является server-operation. Нового backend/RPC/хранилища/provider route нет. Три client SQL templates: commit с1bind, receipt readback с1bind и indexed due-read с2bind. В triggers есть дополнительные SELECT/INSERT/guards: три client templates не равны трём фактическим внутренним операциям или native read-cost.

## Точная атомарная граница

prepareAnomalyCommit канонизирует bounded JSON и вычисляет request/card/descriptor/plan/state SHA256. SQL entry принимает один JSON. Guard проверяет operation-id/digest и expected_revision. Новый receipt записывается перед bundle; любой последующий ABORT откатывает тот же single SQL statement целиком. Нулевое CAS не превращается в успех. UNIQUE native-record/window предотвращает вторую карточку под другим logical-id. Модель identity явно opaque: raw listing date не объявляется уникальной эпохой листинга.

Карточка, recorded first_known_ts, исходный descriptor и полный заранее заданный LONG/SHORT outcome-plan неизменяемы. Состояние watch/revisions/DRAFT обновляется только следующей revision с matching operation receipt. Source cursor не движется назад; одинаковые часы с другим snapshot отвергаются. Старые provenance/outbox refs нельзя удалять. Full plan содержит16ячеек: оба направления ×1h/4h/12h/24h/3d/7d/30d/90d. State обязан содержать каждую исходную ячейку с её target/status; terminal result не переписывается. Пока есть PENDING, next_check не может стать NULL, в том числе после закрытия watch. Due-index не исключает такой event по watch_active. Этот guard исправляет конкретный author-static orphan counterexample до первой семантики; он не квалифицирует сами outcome evidence.

Exact retry с тем же operation-id и digest сохраняет первый receipt, даже если текущее состояние уже новее. Другой digest под тем же id — отказ. INSTEAD OF trigger может вернуть meta.changes=0 даже после успешной записи: adapter не использует этот счётчик как domain ACK. Indexed readback связывает operation/request/immutable hashes/first-known/revision/plan/current state. Проверка SHA делается adapter; SQL проверяет структуру/равенство и ограничения, а не криптографическую подпись. Generic bridge по-прежнему предполагает доверенного обладателя текущих credentials; эти constraints не новый механизм authentication.

После transport failure adapter сохраняет UNKNOWN_COMMIT_ACK и запрещает новый operation-id. Один отсутствующий readback — ACK_NOT_OBSERVED, не доказательство отсутствия commit. Все фактические/unknown расходы остаются в том же instrumented DATA_DB. При unknown_ops>0 дополнительный SQL закрыт; чистая сверка сохранённого receipt не является разрешением нового native запроса. Повторное чтение/попытка требуют реального текущего parent admission после штатного разрешения unknown, без обнуления счётчиков.

Новые таблицы защищены от удаления до отдельной квалификации retention. Это сохраняет активные события и receipts; это НЕ доказательство бесконечной ёмкости. Outbox сейчас только DRAFT/NOT_APPROVED/actual_send=false. Sender lifecycle, UNKNOWN_SEND reconciliation и переход к READY/SENT требуют отдельного утверждённого transport/формы; server-operation этого пакета не разрешает отправку. Нативное подтверждение first-knowledge, instrument epoch, installed schema и admission остаётся false в returned data.

## Связь с существующим producer

Одна монета/упорядоченные часы сами по себе недостаточны. Ошибка parse/сравнения не создаёт новую привязку. Это исправляет конкретный ROOT STATIC F2 counterexample до первой семантики; реальный native incident не заявлен. capturedHtxAnomalyBasis читает уже полученные minute/metadata objects, исходные часы и bounded decoded-text hash; не вызывает сеть/SQL и не меняет старые ответы или signed-tape persistence. Дополнительные parse и parsed-payload hashes обрабатывают только текст в прежнем1MiB TEXT_HASH_RECORDED bound. CPU/heap/задержка и transient allocation не измерены и не объявлены бесплатными.

## Admission и стоимость

Каждый WRITE/READBACK/DUE перед SQL читает текущий usageSnapshot, требует unknown0, явную численную incremental projection от caller и живой admit callback с сохранением downstream reserve. Изменившаяся во время admission usage закрывает вызов. Используются тот же parent DATA_DB/R2RUN, текущие actual counters, day/source/manual/next-full guards. Прошлый admission.allowed JSON не token. Никакой новой provider reservation/alias/пула для чтения уже полученных объектов нет.

В нормальном commit:1D1bridge WRITE +1READBACK, минимум два логических изменения таблиц плюс indices/triggers. Retry: те же два client statements, даже если новые строки не появились; бесплатно не считается. WRITE с поздним unknown/превышением projection сохраняет write reply и останавливается до второго SQL. Denied preaction даёт0statements. Transport unknown после попытки даёт1attempt и0automatic recovery SQL. Indexed due-read — отдельный1statement/2bind под собственным admission. Nodefixture задаёт CONTROLLED usage, не native R/W/plan proof. Receiver row limits не являются read-cost bound.

Сценарии ниже — расчёт будущего режима, не существующая квота. При сохранении каждого5минутного water-mark U=288×A+E commits/day, где A — активные/ожидающие поздних исходов events, E — новые карточки. С due раз в5минут client SQL=2U+288. Для A16/E4 получается U4612,9512client SQL/day и9224логических table mutations. Для A128/E100:U36964,74216client SQL/day и73928логических table mutations ещё до MAIN/LIQ/прочих потребителей. Последний вариант уже сопоставим с общим70000W и не может считаться допущенным. Native counters могут отличаться из-за guards/index/triggers; фактический запас здесь UNKNOWN.

Bundle JSON части ограничены32768+2048+8192+65536bytes; combined request дополнительно ограничен131072bytes. Эти предложенные per-operation bounds не повышают существующие project caps и требуют root принятия. Compact receipt хранит ids/hashes/scalars, без полного state на каждый tick; при условной оценке1KiB/receipt это около4.5MiB/day и36.1MiB/day значений для двух сценариев, без SQLite/index/page overhead. Эту оценку нельзя выдавать за физический размер D1. Накопление receipts без квалифицированного expiry ограничивает sustained activation. Покупка памяти, nominal Paid и statement count не доказывают общий остаток.

Перед активацией root нужны actual installed-schema/readback, native row/byte/CPU/heap cost на whole-account admission, защищённые refs/retention, latency/backlog/recovery и точная sender роль. Physicalstorage и ENTRY-followup owner deferrals этим не возобновляются.
