# Только подготовка неизменяемой версии для текущего отчёта

Конечная задача координатора от22 октября: получить проверяемый путь к будущему реальному immutable candidate version ID, сохранив действующую Paid-привязку strict06603/7011. Это обслуживает текущую последовательную приёмку REPORT+Telegram; затем LIQ, затем native anomaly, затем остаток full17. Пакет не включает разработку native anomaly, ENTRY follow-up или физических storage tests.

Источник — свежий main79aa40ca47f49c190fddd6221d1ecff44825bb8d. Действующий release CLI b959 и Paid provenance5b172 останавливают внедрение c327 до первого CF вызова. Старые618/35 и614/21/611/33 проверки приняты и не повторяются. Все quotas/reservations/unknown1, стратегия, формы, исходные часы, Paid, cursor710 и две OWNER deferrals сохраняются.

Предложение ограничено существующими tools/rollout-correlated-sql-bridge-20261022.mjs и .github/workflows/current-bridge-module-inspection-20261016.yml. Новый stage-only export — stageCorrelatedSQLBridgeOnly({plan,adapter,guard,save,clock}); параметры adapter/DTO согласуются с ROOT до реализации. Старые квалифицированные функции и defaultfalse поведение сохраняются; новый execute_correlated_cost_stage по умолчанию false и исключает остальные flags.

Stage означает один POST immutable version upload без POST deployments, PATCH settings/script-settings/logging, DELETE, SQL, provider, Worker invocation, MAIN/manual или Telegram. Исходник c327 получается из exact strict06603 существующим helper67b. Старый active version7011/deployment/module/settings/bindings/secret inheritance/crons/runtime должны остаться точными. Перед upload latest должен совпадать с active; чужой dormant latest запрещает stage. Reader заранее кэширует исходные bytes старой активной версии и после stage связывает settings с immutable OLD version, а не с dormant latest.

CF OpenAPI граница, которую координатор проверил до проектирования: upload version не разворачивает её; bindings_inherit=strict наследует LATEST upload. GET version/list не гарантирует annotations. Поэтому известный успешный ответ на собственный upload с реальным native version ID является ownership carrier. Затем требуются actual metadata/resources и latest/content/latest bytes, exact c327 и неизменность old active. Request annotations сохраняются только как запросное намерение; нельзя выдавать их за прочитанные native поля.

Если upload ACK потерян, разрешено одно ограниченное наблюдение. Найденные latest ID, хеш и native clock не доказывают владение. В текущем API такой результат остаётся OWNERSHIP_UNKNOWN; нельзя переименовать его в known ACK, повторно загружать, активировать, удалять или перезаписывать чужое состояние. Новый реальный ownership carrier потребует нового точного поручения координатора. Ни ID, ни nonce, ни хеш не означают quota grant, SQL cost closure или восстановление старого unknown.

Намерение с operation ID/head/owner и временем сохраняется до upload. Guard/admission проверяет currentmain/all4/ownscope/fence/generation/headroom перед каждым I/O, включая GET внутри adapter. Пределы текущего контроля <=40CF и<=40GH, whole164 и manual24 не повышаются. Native stage выполняет только ROOT после новой FIRST общей проверки, required automatic PR/main и exact readback. Сырые settings, module bodies и secret values не попадают в Git или proof; proof содержит ограниченные безопасные поля и fingerprints.

Один новый runBridgeStageOnlyConnected({runtime_root,baseline_runtime_root,repo_root}) будет подготовлен как UNEXECUTED callable с actual CLI consumer и контролируемым CF transport, не со старым test export. Runtime аргументы — assembled ROOT. Источник отдельно готовит фактический ordinary caller opt-in; текущий baseline уже618/SDKcab59/journaldc009. Взаимный targeted peer новых частей один раз, затем только ACK точечных исправлений.
