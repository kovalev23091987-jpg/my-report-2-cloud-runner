Единица — instrument_id+wave_id. Обновление, квитанция, повторная запись или повторение той же волны в другом пакете не создают независимый эпизод. Сохранённые raw/draft используются для проверки происхождения, а в будущую статистику допускаются только исходные карточки по политике D/ROOT.

## Исполняемые проверки

`analytics/cohort-audit.mjs` экспортирует:

```js
auditCohortSample(records, {as_of_ts, split_plan: {split_ts, declared_ts, plan_ref}})
auditPairedAnalyses(pairs, {as_of_ts})
```

`auditCohortSample` использует принятый `summarizeOutcomes` для исходных контрактов/дублей/исходов и добавляет проверки пригодности первоначальных признаков и временного исследования. Бounded limits: 2048 записей, 64 признака на запись, 2 MB сериализованного входа; пары — до 64. Это границы работы инструмента, а не новые торговые пороги.

Предложенная опциональная sidecar-форма `record.audit_meta` (общие contracts не менялись):

```js
{
  analysis_sha256, implementation_sha256,
  origin_anchor: /* сохранённый immutable anchor D с той же origin/analysis_sha256 */,
  // Для UNSENT: terminal event/known clocks, state и evidence_ref.
  unsent_terminal, possible_send_ref,
  feature_schema_version: 'pump-initial-features-v1',
  features: [{name, value, absence_reason, source_event_ts, received_ts, known_ts, evidence_ref}],
  forecast: null | {
    value_pct, model_version, training_manifest_sha256, created_ts,
    training_cutoff_ts, trained_through_label_ts,
    mode, map_mode, rules_version, profile_version, feature_schema_version
  }
}
```

Наличие этих полей и OBSERVED-флага само по себе не доказывает подлинность raw, прогноза или native provenance. Внешнее подтверждение не имитируется. Схема проверяет форму/согласованность заявленного происхождения; окончательная аутентичность требует сохранённых первичных доказательств ROOT. Значения forecast в тестах — только синтетические граничные входы валидатора; это не оценки и не результаты аудита рыночных данных.

Проверяется whitelist первоначальных признаков шести блоков, типы и предметные диапазоны, null с причиной, уникальность имён, event≤received≤known≤t0, привязка к карте/режиму и исходному хешу. Нельзя подать outcome/будущую доходность как первоначальный признак, изменить frozen признаки/версию на обновлении или перенести прогноз с MAP на NO_MAP. UNKNOWN-публикации не превращаются в SENT/UNSENT; для возможной отправки нужен связанный источник доказательства. Активный никогда не отправленный draft не заменяет terminal FIRST_READY.

Временные TRAIN/HOLDOUT/PURGED в результате описывают положение исходных волн во времени. **Фактическая структурная пригодность** отражается отдельно в issues, structurally_usable и clean_*_wave_keys; сырые временные счётчики нельзя использовать как обучающую выборку без этой проверки. UNKNOWN и незавершённые исходы не становятся победами или проигрышами. Обновления одной волны остаются в её исходной части.

Для обучения нужны полностью созревшие четыре часа и доступная к split метка. Ранний HIT, чей полный горизонт пересекает split, исключается из обучения. Поздно полученная метка также исключается. Для holdout нельзя обучить прогноз на данных после frozen split, даже если они появились до конкретной поздней holdout-карточки. Ретроспективно записанная граница не считается предобъявленной.

Разделение сохраняет mode, publication, map_mode, rules_version, profile_version, evidence_class, implementation_sha256, feature schema и модель. Инженерные минимумы 300/20/14/100 переиспользованы из `PROPOSED_SAMPLE_REQUIREMENTS`; проверяются внутри когорт, с московскими календарными днями и поздней временной частью. Это предложенные условия, а не доказательство качества. Каждый результат всегда сохраняет calibration_validated=false/publication_allowed=false/probability=null: этот инструмент не обучает и не принимает модель.

## Как проверять полезность и затем калибровку

1. До последующего периода зафиксировать версии, правила выбора эпизодов, схему признаков, границу обучения/holdout, сопоставляемые варианты и заранее согласованные пределы доверительного диапазона/ошибки калибровки. Эти численные пределы не выдумывались в F.
2. Начинать с понятных состояний отката из ТЗ; при малой выборке использовать заранее описанную более общую группу сценариев, сохраняя обязательные различия режимов/карты/доставки/версий. Не создавать десятки мелких категорий ради удачных результатов и не объединять несовместимые когорты ради 300.
3. Сохранять исходные признаки и, когда появится обоснованная модель, её прогноз до исхода. Не обучать модель и не подбирать категории на holdout. На последующей части проверять соответствие прогнозов фактам и заранее записанным границам качества; UNKNOWN и пропуски показывать отдельно.
4. Для карты/другого дополнительного блока сравнивать варианты одного кандидата с теми же t0/P0 и обязательными данными, доступными на тот момент. Метод `auditPairedAnalyses` отвергает изменённый origin, другую реализацию внутри пары, будущую карту, несвязанные raw-входы, отсутствие заявленного контраста и изменение посторонних входов.
5. Варианты могут отличаться готовностью/планом/текстом, но не считаются отдельными независимыми победами. Сохранять и варианты с отказом, чтобы не отбирать только успешных кандидатов. Разница долей успеха несопоставимых наборов не устанавливает пользу карты. Сравнение поведения пары A не является доказательством улучшения точности или прибыли.
6. Работоспособность источника (свежесть, покрытие, задержка, стоимость) учитывать отдельно от аналитической пользы. Новые карты ради размера выборки не собирать. Новые настройки сначала проверять без влияния на сообщения; автоматического переписывания стратегии нет.
