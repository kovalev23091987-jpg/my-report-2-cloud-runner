# AJ — первый genuine production SENT

**UNEXECUTED / SENT=false:** actual receipt ещё не передан. Это одна страница условий для ROOT, не новый admission. Основа — существующие AHv2/AG actual, PUMP_DELIVERY_V2 и сохранённый journal. Новых проверок/adapter/IO нет.

- **Original.** Exact run_id/request_id, analysis_key=`pump:analysis:SHA256(JSON.stringify(analysis))`, отдельные input/original hashes, implementation pin и исходные analysis_ts/saved_ts. purpose=PRODUCTION, evidence_class=OBSERVED; identity/mode/wave совпадают. Старые acceptance239/240/trial IDs не доказывают production SENT; их originals не переписываются.
- **Право отправки.** Этот original READY, прежние ownerfilters и conservative full-plan≥10 пройдены, publish запрошен, TG flag/admission действуют. NOT_READY или publish:false → **0 TG attempts**, без fallback на другой original. AG actual-one остаётся NOT_READY; повторять его ради READY нельзя.
- **Сохранённая карточка до HTTP.** PK `pump:card:<card_id>`, schema PUMP_DELIVERY_V2; source_input_key равен этому analysis_key, card.analysis без source_input_key точно равен original.analysis. card.text===original.card_text; text_hash=SHA256(UTF8(text)); card_id=`PUMP:SHA256(instrument_id|wave_id|text_hash)`. Другой прежний primary_card при дедупликации не является новой отправкой текущего original.
- **Время и валидность.** analysis_ts≤saved_ts≤card.created_ts≤durable send_started_ts≤confirmed_ts. Обязательные revalidate/expiry/owner checks и AUTO window соблюдены. Actual Telegram HTTP начинается **до card.expires_ts** и в текущем bounded admission; durable marker перед budget CAS сам по себе не является точным HTTP-start witness. Ответ/ACK может прийти после expiry: это не делает своевременную отправку просроченной и не продлевает исходный TTL.
- **Telegram ACK.** Успешный HTTP и body.ok=true, положительный message_id, result.chat.id точно равен утверждённому recipient. Текст outgoing payload соответствует сохранённому text_hash по exact pinned sender path; если ACK содержит text — сверить и его. Токен/URL с токеном/recipient/raw text остаются private, публично только хеши и статус.
- **Durable SENT readback.** Сохранённая card.state=SENT, message_id совпадает с ACK. receipt.card_id/text_hash/recipient/message_id точно совпадают с карточкой и отправкой; confirmed_ts фактический, send_started_ts не позже него. Exact PK readback подтверждает неизменные text/hash и receipt. Отдельный journal SENT event связан с теми же analysis_key/card_id/message_id/receipt_ref и confirmed_ts; исходная ссылка исходов сохранена. Mature4h/модель/калибровка не являются условиями первого SENT.
- **Native ACK и расход.** Тот же run/reservation: native_receipt=FINALIZED с exact readback, measured R/W/requests и SQL unknown=0; TG HTTP attempt/CONFIRMED либо UNKNOWN учтён в общем ledger, без возврата SPENT/unknown/резервов. Само успешное сетевое сообщение без сохранённого receipt/readback ещё не завершает эту приёмку. UNKNOWN/потерянный ACK не повышается в SENT и не даёт права слепого resend.
- **Итог ROOT.** Связать private original→same saved text→actual message_id/recipient→durable receipt/journal→native finalization. Публично передать counts/hashes/reasons и exact artifact pin; частичный путь обозначить конкретной недостающей связью. Стареющий после успешной отправки original остаётся историческим SENT; его не омолаживать и не восстанавливать как current сигнал. Новые данные создают новый immutable original по прежним правилам.
