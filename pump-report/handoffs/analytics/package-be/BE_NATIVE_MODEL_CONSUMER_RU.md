## Решение по этому конкретному срезу

В текущую карточку BingX нельзя передавать его цены как зоны, цели, входы или ликвидации BingX. У среза пока нет доказанного canonical asset join и сопоставимости native USD-цен с BingX USDT; у 100 ценовых центров нет явных границ интервалов. Кроме того, оригинал уже старше текущего model_map-предела. Наличие полученного ответа не делает карту USABLE/PARTIAL.

Полезная новая информация есть: получен именно внешний расчётный срез будущих принудительных ликвидаций для native HYPE на Hyperliquid; это не история исполненных ликвидаций. Сохранить его происхождение, модельный характер, исходные часы, охват и причины непригодности можно в существующих полях карты. Полученный исторический ответ не доказывает рабочий recurring route, coverage 550, карту DOOD, AUTO/SENT или полезность для исходов.

Не складывать общие totals с bins или flagged_notional; не суммировать повторные snapshots как независимые деньги. Не делать long/short imbalance направленным прогнозом.

Равномерный шаг центров, соседние середины, lower=upper=center либо округление к tick не заменяют доказанные границы. Даже формально допустимая нулевая ширина Zone не разрешает приписать всему bin точную цену ликвидации.

## Точная связь с существующими полями

Новый обязательный contract не нужен для сохранения этого результата.

- input.liquidations.status/reason: допустимый enum и точная причина непригодности. Для исторического capture применим STALE; для свежего, но неквалифицированного native ответа — ABSENT с причиной непригодности, не NOT_CHECKED и не USABLE. PARTIAL имеет смысл при наличии пригодной части карты, а не просто удачного ответа.
- input.liquidations.zones=[]: пока нет квалифицированных зон. Не создавать фиктивные lower/upper.
- checked_sources: существующее место для route/native context, результата проверки и evidence_ref. Форму элемента фиксирует ROOT/SOURCE; consumer её не переинтерпретирует.
- coverage: существующий объект для ограничений охвата и компактной исходной provenance: native venue/family/ID, source=raw, basis=EXTERNAL_MODEL, computed/received/base-block/base-time-null, requested/returned-bin counts, original SHA/evidence_ref и перечисленные blockers. Имена дополнительных диагностических ключей согласует ROOT; это не новый активный формат, authored BE.
- selectZones (zones.mjs:78–79) сохраняет status/reason/coverage/checked_sources в result.liquidations, оставляет map_mode=WITHOUT_MAP и qualified_zone_count=0 при пустых zones. Историческая причина остаётся в машинном результате.
- Fact не требуется переименовывать в open_interest/trades/funding: explainOptionalFacts (context.mjs:60–83) понимает только эти существующие виды. Произвольный новый kind формально можно поместить в envelope, но он не станет автоматически выводом или строкой карточки.
- explainMapPlan (context.mjs:86–96) использует только пригодные zones_up/down; пустая карта не создаёт confluence и не влияет на структурный план.

Обычный путь карты уже достаточен после действительной SOURCE-квалификации: Zone.asset_id — доказанный canonical asset, venue/market_id остаются Hyperliquid/native, basis_type=EXTERNAL_MODEL, source/primary_provider=исходный поставщик, evidence_ref — точная lineage, lower/upper — доказанные границы в сопоставимой цене, price_currency=USDT только после доказанного mapping, magnitude_unit=USD можно оставить USD. USD-номинал не требуется насильно переводить в USDT, чтобы показать единицу честно. Origin ESTIMATED относится к Fact, если ROOT выберет Fact envelope; Zone использует basis_type.

selectZones (36–40) требует доказанные identity/clock/usable/цены; внешняя площадка требует price comparability evidence. Наличие одной строки evidence_ref не является самим доказательством: SOURCE должен дать правильные границы и mapping. Native USD-цена без перевода не проходит этот путь. Model_id/version сохраняются только если доказаны; неизвестная версия остаётся null и запрещает merge по mergeKey (18–23), а не подменяется API header или snapshot timestamp. Существующий formatter уже показывает источник/биржу, расчётную модель/версию, величину с единицей, время и ограничения каждой пригодной зоны.

## Один новый доказанный display gap и минимальное предложение ROOT

Доказанный gap узкий: renderer в analytics/index.mjs:63 при WITHOUT_MAP всегда печатает общее «Карта ликвидаций недоступна…». Он не выводит result.liquidations.reason/checked_sources/coverage. Поэтому сохранённая точная причина «получен внешний срез, но пригодные зоны для BingX не подтверждены» теряется для читателя. presentation.selectUserNarrative также не читает произвольный native-model context. Просто заполнить coverage или добавить неизвестный Fact kind недостаточно для появления информации в карточке.

Минимальное совместимое предложение — только расширить существующую WITHOUT_MAP строку в analytics/index.mjs:63 коротким allowlist-пояснением по существующим status/reason. Например, reason для полученного, но не квалифицированного native-model ответа может дать текст: «Получен внешний расчётный срез; пригодные зоны для BingX пока не подтверждены». Для status=STALE и подтверждённой причины устаревшего модельного среза: «Полученный расчётный срез устарел». Точные коды фиксирует ROOT. Не печатать свободный raw/provider reason и private refs, не заявлять конкретный HYPE asset в карточке до доказанного join. Короткие безопасные пояснения должны действовать и в full, и в compact ветке, сохраняя лимит карточки и все обязательные поля.

Эта правка не требует новой схемы, поля, маршрута, helper-файла, threshold, score, gate или новой selection matrix. Она не делает native данные пригодными и не меняет map_mode. Обычный manual refusal не надо расширять ради этого payload: причины отсутствия основной идеи остаются основными.

Числовую отдельную summary-строку native модели сейчас не предлагаю: текущий capture устарел, asset join не доказан, total/flagged смыслы легко спутать с близким риском. После свежего доказанного join можно честно подписать USD/model/Hyperliquid/time/limited-base-state, но это отдельная конкретная задача ROOT с согласованными полями. Не нужно строить параллельный consumer только ради этого ответа. В BE никакой кодовой правки нет.

## Конкретные следующие inputs

Для полезной короткой отметки о внешнем ответе достаточно существующих status/reason и provenance в coverage; renderer-предложение выше делает причину видимой. Для количественного model context конкретного актива нужны SOURCE exact native→canonical asset join, method/unit/total/flagged semantics, исходные часы и ROOT acceptance ограничений базового состояния. FX/межбиржевая price comparability не нужны, если остаются только явно подписанные native USD агрегаты без цен/дистанций/плана.

Для включения цен в существующие зоны дополнительно нужны: документированная геометрия bins или исходные пригодные интервалы; native price currency и доказанная contemporaneous сопоставимость с BingX USDT (одного USD→USDT FX недостаточно, если есть межбиржевой basis); ограничение ошибки/точности; модельная lineage/охват/дедупликация. Counts и totals не заменяют эти inputs. Нельзя без mapping считать above/below native mid сторонами относительно текущего BingX reference или искать пересечение с USDT entry/exit.

Для новой текущей карточки потребуется новый допустимый по времени нормализованный факт из отдельно разрешённого маршрута; BE не заказывает и не выполняет новый вызов. Missing bin geometry/FX сами по себе не запрещают честный неценовой native context после остальных квалификаций, но запрещают превращать его в зоны BingX.
