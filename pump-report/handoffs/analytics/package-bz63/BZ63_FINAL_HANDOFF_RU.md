**BZ62 подтверждён в узком scope; прямое внедрение proposal пока не готово из-за version/read routing.** Статически сверены все16 frozen payload hashes BZ62: proposed — e329280fa138a3a01e98cb99713dc5e93b3f2cee4d1dae95f7c937ec371b6de7, base — 6f3ad60c9f235512bd762133c56f5e662fe9b78cbc8eec0cf76b76dc44942ec9. Guard подтверждает именно supplied closed rows: текущий original fact/header, seed и12 baseline окон, сопоставимость, исходные часы и совпадение агрегатов. Для этого значения RECONFIRMED_SUPPLIED_CLOSED_ROWS нового ложного bound статически не найдено. Но он не знает первоначальный seed fact_id/evidence и hash каждого первоначального baseline окна. Два разных набора прошлых окон могут иметь одинаковые median/range. Поэтому это не доказательство first-source authentication или первого знания; external_provenance_authenticated остаётся false. Положительные fixtures подтверждают внутренне согласованную синтетическую цепочку, а не настоящую provider/unit qualification.

Rolling IDs имеют два разных случая. Новый original с согласованными новым fact_id/evidence/header и часами≤его T0 может подтвердить полностью присутствующие старые строки — это вывод из условий кода, отдельного synchronized-ID positive в BZ62 не было. Подмена facts у старого immutable original оставляет старые IDs/evidence или новые часы>T0: будет UNKNOWN. Переписывать analysis для согласования нельзя. Полный original, доступный где-то ещё, не является supplied input и не разрешается автоматически. Иной профиль, SHORT_HISTORY, отсутствующие row refs/старые metadata, дублированный declared fact_id, overflow1441 или недоказанные units также остаются UNKNOWN. Даже проверяемые seed/current numerator остаются UNKNOWN без всей baseline: guard консервативно объединяет все8 features. У current-to-seed ratio дополнительно обязателен declared current5m range.

Два конкретных препятствия прямому внедрению:

1. Proposal сохраняет schema/key v2. При той же analysis_sha изменяются feature payload/digest. retained-capsules.original() повторно строит капсулу и для remember(), и при record() зрелого исхода; immutable() выдаст IMMUTABLE_RETAINED_CAPSULE_CONFLICT, если по v2-ключу уже лежат старые bytes. Fixture BZ62 не содержала store с ранее сохранённой капсулой, поэтому этот переход не проверен.
2. readFeatureCapsule байт-в-байт прежний. Он принимает старое v2 bound=true по общим header clocks и не проверяет source_window_status/ranges. Новый deploy или успешный digest не делают legacy seed verified. Actual downstream model use здесь не исследован — UNKNOWN. prepareOutcomeCapsule и summary links дополнительно содержат hardcoded v2 keys/schema, поэтому одной замены FEATURE_CAPSULE_VERSION недостаточно.

План для ROOT, без реализации в BZ63:

- Выделить новым капсулам отдельные schema/key v3 и явную binding policy вне origin. Старые v2 bytes, ключи, analysis/input и saved implementation pin не менять.
- Выбирать codec по неизменяемой metadata нового original/зафиксированному writer epoch и существующей feature reference. Не выбирать текущий writer по Date.now при позднем outcome. Старые originals без v3-маркера остаются legacy; marker записывается только вместе с действительно новым original после интеграции.
- Разделить raw audit view и verified seed view. Старые v2 доступны для аудита/численных labels, но в verified view их seed-поля — LEGACY_SOURCE_WINDOW_UNVERIFIED/UNKNOWN. Это производное представление; записанные старые числа не обнуляются и не переписываются. Новый reader проверяет policy/status/ranges/header clocks и допустимую writer implementation; одного bound=true недостаточно.
- Явно маршрутизировать feature/outcome/summary-link schema и namespaces: legacy v2 сохраняет свои ключи, новые v3 используют свои точные feature key/hash. origin остаётся точным signal.origin; T0/P0 и+4h не пересоздаются. Старый v2 payload не регенерируется новым writer. Если у legacy original отсутствует сохранённая капсула/reference, вернуть явную capsule-unavailable/legacy причину, сохранив основной per-wave outcome/summary; не создавать fake verified v3 и не переклассифицировать численный исход.
- Не выполнять массовую миграцию, дополнительные source/native lookup, cleanup, удаление refs или изменения текущего publication-пакета. Полные, но не представленные/неразрешённые originals остаются UNKNOWN. ROOT отдельно владеет canonical integration, budget/read-path и новым artifact; BZ62 остаётся доказательством компонента по точному e329, а не всего version/store перехода.
