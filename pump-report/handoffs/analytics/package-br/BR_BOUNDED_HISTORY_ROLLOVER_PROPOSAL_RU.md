При пустой начальной истории и условных 24 успешных выдачах в сутки: 8 × 24 = 192; первые 8 выдач девятого UTC-дня заполнят 200, девятая выдача этого дня получит `SURPLUS_LOGICAL_GRANT_LIMIT`. ## Предлагаемый минимальный протокол для будущего решения ROOT

1. **Версионировать логическую схему.** Оставить `automatic_surplus_grants` рабочим индексом максимум 200. Добавить в существующий resources монотонный `automatic_surplus_issued_by_day[UTCday]`, а в существующее KV-хранилище — ключ `pump:surplus-spent:<sha256(run_id)>`. Ключ содержит полный run_id для проверки совпадения, факт единственной выдачи и затем полный терминальный CLOSED. Несовпадение идентичности/коллизия означает отказ. Это отдельная долговечная запись доказательства, не новая физическая БД или storage cleanup. Использовать имеющийся `pump:run:<id>` как единственное доказательство нельзя без отдельного изменения его перезаписывающего writer.

2. **Выдача атомарна с доказательством расхода.** Будущий consumer использует существующий `atomicPair(resources, run-ledger)` — store:60–94. Новая выдача одновременно создаёт OPEN в рабочем индексе, доказательство выдачи в ledger и увеличивает счётчик исходного UTC-дня ровно один раз. Все три ограничения 200/24/1 проверяются внутри CAS. Уже записанный run не получает новую выдачу после переноса CLOSED. Повтор того же OPEN может вернуть существующий допуск только при совпадении кандидата, стоимости и доказательства; это не новая выдача. Другие day/month/provider/plan/pacing/unknown/outstanding поля сохраняются без уменьшения.

3. **Переносить максимум одну подходящую запись за уже допущенную обычную операцию.** Нового cron/фонового задания не требуется. Подходит только CLOSED прошлого UTC-дня с `hold_until≤now`, `native_expires_ts≤now`, положительным подтверждением закрытия и полным readback, без связанного outstanding/UNKNOWN/неизвестного ACK. При недостаточных ограниченных доказательствах запись остаётся на месте. OPEN, UNKNOWN, CLOSED текущего дня и любые неквалифицированные записи не переносятся. При заполненных 200 и отсутствии подходящего CLOSED сохраняется отказ.

4. **Сначала сохранить доказательство, затем убрать только копию из рабочего индекса — одной атомарной операцией.** В `atomicPair(resources, ledger)` перенести CLOSED целиком: исходные created/closed/day/expiry/hold, candidate/run, native evidence, activation ref, logical_spent, original/remaining/consumed и providers. Ledger должен совпадать с доказательством прежней выдачи; legacy ledger создаётся из полного авторитетного CLOSED в той же операции. При конфликте — отказ. Подтверждённый ACK и FULL readback предшествуют дальнейшему использованию освобождённого места. При неизвестном ACK применяется существующий консервативный учёт неизвестности; нельзя угадывать результат, повторно выдавать место или возвращать расход. Данные CLOSED остаются в ledger, native-история не удаляется.

5. **Legacy-переход только из полной истории.** До первого переноса одноразовый CAS с маркером версии фиксирует суточные количества по полному сохранённому индексу71. После этого счётчик увеличивается только при новой выдаче и никогда не пересчитывается вниз по укороченному индексу. Если обнаружены предшествующий перенос без счётчика, неполная история, неверный маркер или противоречие ledger/индекса, нужен отказ и отдельное согласование. Значение 0 вместо неизвестного запрещено.

После переноса только не удерживающего прошлодневного CLOSED расчёт holds по рабочему индексу эквивалентен прежнему. CLOSED текущего дня остаются, поэтому дневной допуск и защита будущих BASE сохраняются. Расходы текущего/прошлых дней и месяцев не меняются; освобождается только позиция рабочего индекса.

## Границы решения

Это явное предложение изменить организацию логической истории, требующее решения ROOT, а не скрытое повышение 200: каждый рабочий индекс остаётся ≤200, запись ledger ограничена одной выдачей/терминальным доказательством на run. Общее число долговечных доказательств и суточных счётчиков со временем растёт. Постоянный общий объём хранения и бесконечная точная защита от повторного run одновременно этим не доказаны. Если 200 трактуется как предел всей долговечной истории, безопасно забывать старые spent run нельзя без другого долговечного доказательства. OWNER deferral физического storage остаётся открытым; новый storage/retention/throughput тест и ENTRY lifecycle не входят в BR.

Будущие чтения ledger, атомарные записи, FULL readback, сериализованные байты и возможные CAS retries требуют собственной фактической admission ROOT с сохранением всех резервов. Два ключа не являются доказательством двух SQL или billed rows; текущий atomicPair допускает до пяти попыток. BR не выдаёт LOOKUP14/CONTROL7/METADATA3 и не разрешает никакого нового native IO. Подготовка schema migration, кода, affected test или cleanup здесь не начата. Сохранены 9 пауз, 2 OWNER deferrals, исходные часы, unknowns и все прежние расходы.
