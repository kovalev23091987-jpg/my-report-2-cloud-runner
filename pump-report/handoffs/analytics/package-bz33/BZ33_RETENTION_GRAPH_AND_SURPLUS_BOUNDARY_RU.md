## Что действительно означает лимит200

`candidate-surplus.mjs:makeSurplusGrant` объединяет под `SURPLUS_LOGICAL_GRANT_LIMIT` три причины: сохранено200 грантов, достигнут суточный максимум24 или уже есть один грант этого запуска. Старый grant проверяется раньше: OPEN идемпотентен; CLOSED/UNKNOWN не выдаётся заново. `surplusGrants` допускает ровно200, а >200 уже считает повреждённым/непригодным состоянием.

В двух сохранённых фактических снимках29Oct:58 записей, все CLOSED;5 записей текущего UTC-дня. В запуске `9cf8cdfa-99bc-4ea0-9c43-595a77ca5623` уже есть grant ON; следующий EVAA получил общий logical-limit. Из трёх условий истинно только SAME_RUN. Следующий снимок запуска `53cb9461-e1ce-4ac5-b41a-99b6ea1c9adb` также58/5, собственного гранта нет; INIT отложен по **SURPLUS_NATIVE_CAPACITY_REQUIRED**, иной причине. Это арифметика уже сохранённых данных, без вызова runtime. SHA исходных пакетов и производные числа — в `BZ33_SAVED_BUFFER_FACTS_V1.json`. Текущая фактическая наполненность UNKNOWN: новых native чтений не было.

Ровно200 исправных записей запрещает **новый условный дополнительный grant**, когда `budget.admitCandidate` дошёл до surplus-ветки. Сам по себе этот счётчик не запрещает обычный base-допуск и не вызывает `makeSurplusGrant` при отправке уже готовой карточки. На обычные бюджеты отдельно действуют реальные OPEN/UNKNOWN/сегодняшние CLOSED holds, расход и защищённые резервы. >200 либо повреждённый grant может fail-closed затронуть и общий `reserve` через `surplusHeld`; это другой случай. Нельзя объявлять историю200 причиной отсутствия обычной доставки по имеющимся данным.

Граф в компактном виде: `source evidence → original analysis+input → card/receipt → journal frozen anchor → signal/outcome → summary record → capsule link → feature/outcome/protected-refs`. Дополнительно `summary head/member/pending → record`, `work member → durable target/evidence`, `resources grant → native/run accounting`. Стрелки означают необходимость исходного узла для последующего потребителя, а не разрешение заменить исходный узел производным.

## Готовый безопасный шаг

`BZ33_SURPLUS_LIMIT_DIAGNOSTIC_PROPOSAL.patch` меняет только три ROOT-файла в виде предложения:

1. `candidate-surplus.mjs` сохраняет прежние allowed/detail и порядок old-grant/native guards; добавляет при общем logical-limit bounded counts и до трёх reasons: RETAINED_RECORD_LIMIT / UTC_DAY_GRANT_LIMIT / SAME_RUN_GRANT_LIMIT.
2. `budget.mjs` переносит этот объект в результат отказа.
3. `runner.mjs` сохраняет объект в `DEFERRED.source_coverage`, чтобы обычный run receipt различал причины без дополнительного SQL.

Все обходы ограничены уже проверенными≤200 grants; reasons≤3, ids/сырые grants не добавляются. Предикат `some(run)` эквивалентен `run_count>0`; cap/run/day и исходные состояния не меняются. Диагностика берётся внутри существующего atomic snapshot, прежний общий reason/detail сохранён. Дополнительных вызовов store/provider/Telegram нет; run receipt может стать немного больше. Это не freeslot/archive/retention activation и не новая native qualification.

Проверены10 точных локальных code-preimages против серверных Git blobs; три target blobs также сверены с новым main. Для каждого patch-target ровно одно текстовое вхождение и SHA до/после. JS/import/product/test/build не запускались. Первый структурный проход остановился на отличающейся локальной копии approval checkpoint: она не использовалась как authority; policy читалась с GitHub `e99bacadedf00a6bc9317eb42835cc05f3dd5594`. Это не ошибка runtime или выполненный тест. ROOT применяет предложение только после своих fresh authority/own и необходимого допуска на одну affected проверку; тест здесь не заявлен. Отдельная установка только ради метаданных не требуется для текущей работы AUTO.

## Что остаётся для настоящего logical archive

BZ26 уже описал контракт (`BZ26_SURPLUS_ARCHIVE_CONTRACT_V1.json`, SHA `bc82641db9b1989f806f50f17650b6e97ad55cc8a005f58b8e3435186d290a59`); он по-прежнему PROPOSED_NOT_IMPLEMENTED_NOT_NATIVE_QUALIFIED. Здесь не выдаётся повторная спецификация за реализацию. Конкретный отсутствующий путь: bounded raw `pump:resources` snapshot с byte hash/revision → проверенный immutable pack → постоянный spent-marker запуска → CAS active-state+commit-intent → reader/readback/recovery. Проверка spent-marker должна участвовать в **каждой** последующей выдаче и быть защищена от гонки с архивацией; отдельный best-effort read до CAS недостаточен. Нужны точная FINALIZED native row с unknown0 и отсутствие связанных outstanding/unknown перед demotion гранта. CLOSED отдельно этого не доказывает. Существующий `get()` читает parsed JSON целиком, не предоставляет такой raw bounded reader/revision. Текущий `atomicPair` и готовые immutable capsules сами по себе не реализуют эту транзакцию.

Копию можно сохранять с TTL=null и originals на месте: отсутствие TTL **не запрещает всякий логический прогресс**. Но перенос записи из active `automatic_surplus_grants` освобождает место только после явного versioned решения ROOT о семантике200 — active records либо вся сохранённая история — с постоянным anti-reissue и сохранением дневного лимита/расходов/unknowns/issued floors/hold semantics. Текущий код читает200 как размер всей map; молча переименовать её в active set нельзя. Прямая approval фиксирует максимум1/run и24/day, а не произвольное снятие этих ограничений при архивации. Это конкретный контракт/решение для ROOT в пределах его authority; автоматическое требование нового разрешения человека здесь не вводится.

Если задача включает **удаление** оригиналов/архива или ограничение общего объёма, отсутствует retention policy по семействам: минимальный период потребителя (аудит/статистика/доставка/исход), точный момент начала срока, максимальный срок/TTL либо явное бессрочное хранение, исключения owner/acceptance/UNKNOWN, перечень входящих reference families, допустимый архивный reader и критерий полного закрытия ссылок. Существующая supplied-only projection этих ответов не даёт. Нельзя самостоятельно выбрать7/30/90дней, принять HIT/terminal/cursor за closure или возобновить отложенное испытание физической ёмкости. Удаление ready-pointer не образец удаления original. Copy-preserving archive может ограничить active map; общий физический объём при этом продолжает расти.
