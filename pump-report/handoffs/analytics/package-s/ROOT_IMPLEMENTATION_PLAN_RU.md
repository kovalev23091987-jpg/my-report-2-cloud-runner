# S — конкретный порядок для ROOT

Код отмены benchmark уже отдельно заморожен: `owner-removal-code-manifest.json`, SHA256 `d308b3720177b738b53dab0f46c1e5fee9882f46884f3955d86ef293abcda7e0`.35 групп полей/наборов,28 скалярных feature-описаний,77 проверяемых ссылок на30 файлов — в `retention-consumer-map.json`. Это анализ текущего кода, не реализация очистки и не повтор полного аудита719строк.

1. **Сначала защита ссылок.** Использовать реальные ключи `pump:card:*`, `pump:journal:*`, `pump:signal:*`, `pump:analysis:*`, `pump:quarantine:*`, work queues и summary head.pending. Граф — `protected-reference-edges.json`. READY/SENDING/RETRYABLE/UNKNOWN, незакрытый исход/аудит, unresolved external evidence_ref и исходные acceptance240 сохраняют свои оригиналы. Нельзя заменить `t0/P0/rules` текущим latest или считать прошедшие4ч разрешением удалить. Старый ENTRY followup и physical capacity не затрагиваются.

2. **Оставить выполненный ordered summary index.** `pump:summary-ordered-head:v1`+`pump:summary-ordered:v1:<16-digit seq>`+`pump:summary-member:v1:<hash>` уже имеют pending-allocation recovery, page≤40 и bounded legacy≤40/10000B. Не повторять его принятые5+2 проверки. `pump:summary-record-index` — сохранённый legacy, не live растущий массив. Продвинутый source_cursor не является watermark удаления: current append/recovery/rebuild всё ещё читает raw summary record.

3. **Следующие реальные растущие work indexes.** `pump:journal-index`, `pump:outcomes-pending`, `pump:delivery-queue`, `pump:manual-queue` сейчас читаются целиком. Ввести отдельные ordered references/membership+head/cursor по тому же existing state PK, с отдельным явным versioned namespace (названия новых ключей — предложение ROOT). Старые массивы сначала читать bounded, сохранять hash/order/count; oversized не обрезать молча. Наличие mature date/queue slot не удаляет UNKNOWN. Смена membership только после durable target+summary/readback; никаких новых provider requests для миграции.

4. **Paged journal вместо бесконечного value_json.** В `pump:journal:<instrument>:<wave>` растут `analyses[]` и `publications[]`. Хранить оригинальные append-only записи отдельно и постраничные ссылки; head содержит wave expiry, terminal/frozen anchor и курсоры. Сохранить first-ready/first-possible-send ordering, tie ambiguity, content hashes, knowledge times и позднее разрешение UNKNOWN. До freeze нельзя оставлять только последний analysis. После freeze поздний receipt всё ещё должен находить исходную карточку.

5. **Feature/outcome capsule до удаления detail.** Реальный writer сейчас сохраняет `{analysis,input}` в `pump:analysis:<hash>`, а summary-record — только `{origin,publication,outcome}`. Нет writer для `audit_meta.features/implementation_sha256/forecast/split`. Поэтому summary aggregate недостаточен для повторной оценки признаков. ROOT может добавить новый immutable sidecar (новый namespace только как явное предложение) с whitelist исходных признаков, null+reason, source/received/known clocks, schema/code/rule versions и original refs. Новая схема нужна для Q price-response/netflow; старую `pump-initial-features-v1` не расширять молча. Benchmark columns owner-disabled: новых values, TTL, requests и reserves для них нет. Старые originals/файлы R не переписывать.

6. **Сохранить per-wave labels и охрану replay.** `pump:outcome:<signal_id>` содержит численные DD, coverage и scenario/entry-area lower-bound. Materialized aggregate хранит преимущественно счётчики known/unknown и не восстанавливает эти распределения. В `pump:materialized-wave:production-v2:*` растёт `record_digests{}`; его нельзя просто очистить после HIT — тогда replay потеряет проверку конфликта. Предложение: отдельное persistent membership по record hash/страницам и closed-wave capsule с прежней contribution; commit пары wave+aggregate остаётся атомарным. `pending_deadlines{}` и `instrument_assets{}` в глобальном aggregate тоже требуют явной scope/page policy, не случайного eviction.

7. **Кандидаты на будущее логическое expiration.** `pump:overview-index` исключает старые часы, но `pump:overview:<slot>` не удаляются. Raw broker `pump:cache:*` может иметь уникальный start/end URL каждую минуту и тоже не имеет GC. Истечение cache-hit TTL лишь прекращает повторное использование, не доказывает ненужность единственного source receipt. После защиты ссылок сначала формировать bounded список eligibility/reasons и verified scalar/archive projection; только затем отдельный ROOT admitted cleanup. `pump:latest-analysis:*` дублирует full analysis и не имеет текущего get-reader; `pump:run:*` в inspected runtime write-only, но внешние audit refs всё равно надо проверить. API `pump:manual-result:*` имеет настоящий reader, его срок нельзя угадывать.

Все approved_delete_ttl_ms оставлены null. Фиксированы только существующие consumer windows: overview1ч; текущий5м+60м baseline;5/15/60м рост;24ч отдельный price proof; исходный4ч outcome. Для полной60м impulse search с полной предшествующей базой нужен охват125мин; текущий source request121строка не обещает FULL для каждого раннего окна, SHORT_HISTORY честно сохраняется. Это не новый запрет/изменение стратегии и не предложение нового сбора.

Неизвестные параметры: срок закрытого аудита/оригиналов, approved immutable archive reader/reference registry, срок ручного ответа, срок source reliability/model manifests.14 календарных дней/300 эпизодов/100holdout — предложенные условия выборки, а не TTL. Storage capacity/throughput здесь не измерялись. Минимум — сохранить реальные исходные признаки и labels пока конкретный consumer/reference не закрыт, а не назначать произвольное число дней.
