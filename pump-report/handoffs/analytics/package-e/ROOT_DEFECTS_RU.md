# E: несовместимости текущего runtime ROOT

Зафиксировано ДО добавления и запуска новых тестов E. ТЗ v2 SHA256 `0674adf8bef087f63ddac8214b8e650ae14410f33970ed4f869c5ab2564975cc`; fresh main `108a5dbdfc670d9a48fbf953811f5aa1b7bc2864`. Проверяется текущий локальный runtime; точные хеши зависимостей будут в qualification.json. Runtime не изменяется этим чатом.

1. `runtime/runner.mjs`, `recordPublished`: немедленный выход для любого состояния, кроме SENT. Вызов после dispatch также только для SENT. UNKNOWN после возможной отправки не создаёт исходный сигнал/оригинал для четырёхчасового исхода. Это расходится с принятой политикой ROOT: первая подтверждённая SENT либо первая UNKNOWN после возможной отправки фиксирует исходную карточку. Запрет повторной отправки UNKNOWN в delivery при этом уже присутствует; тесты должны различить эти две обязанности.
2. `runtime/runner.mjs`, `rememberAnalysis`/`checkOutcomes`: READY-анализы сохраняются, но терминальная никогда не отправленная волна не получает исходный сигнал FIRST_READY и не входит в отдельную UNSENT-статистику. В `pump:outcomes-pending` попадают только SENT. D предоставляет отдельный адаптер; в прочитанном runtime он пока не подключён. Проверка должна воспроизвести первый READY без отправки и последующее истечение той же волны, а не произвольно объявить активный draft сигналом.

Минимальное исправление ROOT: соединить сохранённые анализы/полный журнал публикаций/терминальное состояние волны с D `selectOutcomeAnchor`, сохранять immutable исходный анализ с хешем; регистрировать eligible UNKNOWN и терминальные UNSENT раздельно от SENT. Повторная отправка UNKNOWN не требуется. Источник t0/P0 — выбранная сохранённая карточка, не ACK и не поздний draft. История исхода запрашивается только в разрешённое дневное окно и по исходной цели/сроку.

Статические наблюдения не выдаются за результаты исполнения. Новые E-тесты будут обычными строгими assertions по требуемому поведению; обнаруженные дефекты сохранят FAIL, без skip/todo или подгонки теста под текущую ошибку. Остальные сквозные случаи проверяются независимо. Искусственные нормализованные факты и MemoryStore не являются native/provider/SQL/Telegram proof.
